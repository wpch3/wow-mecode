## 【注意】 执行顺序（最重要，先读这段）

```
先编译，后执行 SQL。顺序反了会崩服。
```

**为什么**（已用 26 项测试实证）：

```
FieldValueConverters.h:59-70   GetNumericValue<T>() 做截断检测
    T result = static_cast<T>(source);
    if (static_cast<DatabaseType>(result) != source)
    {
        LogTruncation(func, meta);   // <- 这里
        return T();
    }

FieldValueConverter.cpp:48     LogTruncation 里是：
    ASSERT(false, "%s on %s field ... caused value to be truncated. Use %s instead.", ...);

Errors.h:68                    #define ASSERT WPAssert
```

非 `PERFORMANCE_PROFILING` 构建下，`ASSERT(false)` 就是**直接崩服**，不是打个日志。

最阴的是这个组合：

| 库 | 代码 | 值 | 结果 |
|---|---|---|---|
| int | GetUInt16 | 4211（老菜单） | **不崩** |
| int | GetUInt16 | 96001（新菜单） | **崩** |

老菜单 MenuID 全都 < 65535，所以**只改库不改码，平时一切正常，等你哪天用了大 ID 才崩**。

反过来是安全的：

| 库 | 代码 | 值 | 结果 |
|---|---|---|---|
| smallint | GetUInt32 | 63001 | 不崩（加宽读窄列安全） |

所以顺序只能是 **先码后库**。

## 二、邮箱：上一版错在哪

### 我的错误

上一版写「`UNIT_NPC_FLAG_MAILBOX` 服务端全库 grep 无处理代码，邮箱只能用 GameObject」。

**那是因为我只 grep 了本地留存的几十个文件，不是全仓库。** 这次拉了完整源码重查，结论完全相反：

```
MailHandler.cpp:39   bool WorldSession::CanOpenMailBox(ObjectGuid guid)
MailHandler.cpp:49       else if (guid.IsGameObject())
MailHandler.cpp:51           GetGameObjectIfCanInteractWith(guid, GAMEOBJECT_TYPE_MAILBOX)
MailHandler.cpp:54       else if (guid.IsAnyTypeCreature())
MailHandler.cpp:56           GetNPCIfCanInteractWith(guid, UNIT_NPC_FLAG_MAILBOX)   ← NPC 完全支持
```

官方自己就有 NPC 邮箱 —— **银之侍从 / 征战联盟传令官**：

```
npcs_special.cpp:2089    case GOSSIP_OPTION_MAIL:
npcs_special.cpp:2091        me->SetNpcFlag(UNIT_NPC_FLAG_MAILBOX);
npcs_special.cpp:2092        player->GetSession()->SendShowMailBox(me->GetGUID());
```

### 你看到的「人类 NPC 且没功能」是怎么来的

两个原因叠加：

1. **GO 184137 在你的库里可能不存在**
   `world_database.sql` 只有表结构，TDB 数据包是另发的。
   全仓库搜 184137，只有 `sql/old/` 的历史文件提过。
   `Object.cpp SummonGameObject()` 查不到模板就 `return nullptr` —— 那次召唤根本没成。

2. **960004「便携邮差」的 npcflag 写的是 `1`**
   只有 GOSSIP，没有 MAILBOX。模型 1300 是人类 Lyria。
   所以它退化成一个只会打招呼的人类。

### v4.0 的修法：双保险

| 路径 | 依据 | 做法 |
|---|---|---|
| NPC | `MailHandler.cpp:56` | npcflag `1` → `67108865`（GOSSIP + MAILBOX） |
| GO | `MailHandler.cpp:51` | 运行时遍历 `GetGameObjectTemplates()` 找 `type == 19`，探到就顺手放一个 |

```cpp
static uint32 s_mailboxGo = 0xFFFFFFFF;   // 0xFFFFFFFF = 还没探测过
if (s_mailboxGo == 0xFFFFFFFF)
{
    s_mailboxGo = 0;                      // 0 = 探测过但没找到
    if (GameObjectTemplate const* pref = sObjectMgr->GetGameObjectTemplate(184137))
        if (pref->type == GAMEOBJECT_TYPE_MAILBOX)
            s_mailboxGo = 184137;
    if (!s_mailboxGo)
        for (auto const& kv : sObjectMgr->GetGameObjectTemplates())
            if (kv.second.type == GAMEOBJECT_TYPE_MAILBOX)
            { s_mailboxGo = kv.first; break; }
}
```

**无论你的 TDB 里有没有 184137，邮箱都能用。**

## 三、字段扩容：改了什么

### 代码侧（6 处，全在 ObjectMgr.cpp）

| 行号 | 原文 | 改成 |
|---|---|---|
| 305 | `uint16 menuId           = fields[0].GetUInt16();` | `uint32 ... GetUInt32();` |
| 306 | `uint16 optionId         = fields[1].GetUInt16();` | `uint32 ... GetUInt32();` |
| 9064 | `gt.mapId          = fields[5].GetUInt16();` | `... GetUInt32();` |
| 9546 | `gMenu.MenuID = fields[0].GetUInt16();` | `... GetUInt32();` |
| 9584 | `gMenuItem.MenuID                = fields[0].GetUInt16();` | `... GetUInt32();` |
| 9585 | `gMenuItem.OptionID              = fields[1].GetUInt16();` | `... GetUInt32();` |

### 库侧（4 条 ALTER）

| 表 | 列 | smallint → int |
|---|---|---|
| `gossip_menu` | MenuID | 是 |
| `gossip_menu_option` | MenuID, OptionID | 是 |
| `gossip_menu_option_locale` | MenuID, OptionID | 是 |
| `game_tele` | map | 是 |

### 为什么改动这么小

因为**下游本来就全是 uint32，smallint 纯属历史包袱**：

```
ObjectMgr.h:800   GossipMenus::MenuID           uint32
ObjectMgr.h:782   GossipMenuItems::MenuID       uint32
ObjectMgr.h:783   GossipMenuItems::OptionID     uint32

GossipDef.h:222   GossipMenu::_menuId           uint32

creature_template.gossip_menu_id   int unsigned（库里本来就是 int）
conditions.SourceGroup             int unsigned
```

**扩容后 MenuID 可以用到 42 亿**，不用再挤在 63001 那个小段里。
建议以后菜单 ID 直接和 entry 对齐（比如 NPC 960004 用 MenuID 960004），好记。

## 五、等级 255：为什么这次没动

你选了「要，一起解开」，但我查完必须先跟你交底 —— **这个不是改库能解决的**。

```
CreatureData.h:309    uint8   minlevel;          ← 结构体就是 uint8
CreatureData.h:310    uint8   maxlevel;
ObjectMgr.cpp:545     creatureTemplate.minlevel = fields[14].GetUInt8();
Unit.h:890            uint8 GetLevel() const { return uint8(GetUInt32Value(UNIT_FIELD_LEVEL)); }
Unit.h:892            void SetLevel(uint8 lvl, bool sendUpdate = true);
DBCEnums.h:53         STRONG_MAX_LEVEL = 255,   // "Server side limitation. Base at used code requirements."
```

更硬的一道墙 —— 怪物属性查表把 level 压进了 8 位：

```
ObjectMgr.cpp:9951    _creatureBaseStatsStore.find(MAKE_PAIR16(level, unitClass));
ObjectDefines.h:106   inline uint16 MAKE_PAIR16(uint8 l, uint8 h)
```

实测（widentest 第 21 项）：**300 级怪和 44 级怪会查到同一条 `creature_classlevelstats`**。

还有客户端那道墙：

```
DBCEnums.h:49         MAX_LEVEL = 100,
                      // "client supported max level for player/pets/etc.
                      //  Avoid overflow or client stability affected."
DBCStructure.h:758    #define GT_MAX_LEVEL 100
```

**工程量**：`GetLevel()` 758 处调用、`uint8 level` 类声明 306 处、`SetLevel` 35 处，外加 `MAKE_PAIR16` 和 DBC 改造。

**好消息**：`tinyint` 的 255 和 `STRONG_MAX_LEVEL` 正好吻合 ——
**你现在就能做 255 级的怪，不用改任何东西**，库和代码是对齐的，不存在"库卡着代码"。

如果你确实需要 255 级以上，我单独开一个 step 认真做，那会是比 step19 还大的工程。
