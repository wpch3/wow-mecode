# 第 7 步 v2：完整替换（推荐）

## 为什么替换而不是修改

1. v1 已经有 5 处零散改动，再叠加修改容易出现「改重复/改漏」（就像 RBAC 那两次）
2. v2 新增 6 个函数、重写判定逻辑，散着改比整体替换更容易出错
3. 替换后只有一个版本，不会有「改到第几版」的困惑

## 你的质疑是对的 —— 实测证明

「同名 ≠ 同一件物品」。我用真实数据结构做了验证：

```
.add 埃辛诺斯战刃
  -> 匹配 2 项：ID 32837(主手 InventoryType=21)
                ID 32838(副手 InventoryType=22)

  -> v2：列候选让你选                                  ✅
```

## v2 的四条规则

| # | 条件 | 行为 |
|---|---|---|
| 1 | 纯数字输入 | 按 ID 直接处理 |
| 2 | 唯一匹配 | 直接给 |
| 3 | 多个但**所有字段完全一致** | 直接给（真·重复条目） |
| 4 | 有任何差异 | 列候选，按推荐度排序，★标最优 |

### 严格身份判定比对的字段

**物品**（任一不同即视为不同物品）：
```
名称 / Class / SubClass / InventoryType(★主副手关键) / Quality
ItemLevel / RequiredLevel / Armor / Description / StatsCount
全部 10 条 ItemStat / 全部 2 组武器伤害
```

**生物**：
```
名称 / Title(副标题) / minlevel / maxlevel / faction(阵营)
rank(精英/BOSS) / type / unit_class / Modelid1(模型) / ModHealth / ModDamage
```

### 推荐度评分（只用于排序，不代替你决定）

```
物品：装等×100 + 品质×500 + 属性总和 + 护甲 + DPS×10
生物：等级×100 + rank×50 + 血量系数×10 + 伤害系数×10
```

## 一个使用技巧

看到候选列表后，**直接复制 ID 再执行**最快：

```
.add 埃辛诺斯战刃
  [推荐] 埃辛诺斯战刃  ID:32838  装等:156 品质:5
         埃辛诺斯战刃  ID:32837  装等:156 品质:5

.add 32837        <- 想要主手就用这个ID
```

这也是为什么规则 1（纯数字直取）很重要 —— 它让「列候选 → 精确获取」
形成完整闭环。
