F30 三个问题一次定位

你报的三件事，根因各不相同，逐个说。

================================================================
 问题1：F29 止血为什么没生效
================================================================

因为客户端走的是【另一个 opcode】。

全服有两个踢人入口（实查 GroupHandler.cpp）：

    :338  HandleGroupUninviteOpcode      按【名字】踢  <- F29 拦的是这个
    :295  HandleGroupUninviteGuidOpcode  按【GUID】踢  <- 你的插件走这个

按 GUID 那个版本，包里【根本没有名字】：

    :301  recvData >> guid;      <- 只有 GUID
    :302  recvData >> reason;

    :335  SendPartyResult(PARTY_OP_UNINVITE, "", ERR_TARGET_NOT_IN_GROUP_S);
                                      ^^ 发的是【空字符串】

"party2" 这个词是【客户端自己填进去的】——
服务端回一个"目标不在队伍"的错误码，客户端拿自己请求时用的
UnitID（party2）拼成提示语显示出来。

所以 F29 按名字拦截，对这条路径完全无效。

----------------------------------------------------------------
 修法：把按GUID版也拦掉
----------------------------------------------------------------

文件 D:\TrinityCore\src\server\game\Handlers\GroupHandler.cpp

搜索原文（约 334-336 行，全文件唯一）：

    SendPartyResult(PARTY_OP_UNINVITE, "", ERR_TARGET_NOT_IN_GROUP_S);
}

void WorldSession::HandleGroupUninviteOpcode(WorldPacket& recvData)

替换为：

    // F30: 不回这个包。
    // 客户端插件会遍历 party1~party4 批量尝试踢人，找不到就刷屏。
    // 这里静默返回，真人玩家点右键菜单踢人时目标一定存在，
    // 走不到这一行，所以不影响正常使用。
    return;
}

void WorldSession::HandleGroupUninviteOpcode(WorldPacket& recvData)

【只是把那句 SendPartyResult 换成 return;】

同理，F29 装在按名字版里的拦截可以保留，两个一起挡更保险。

================================================================
 问题2：「未找到名为卡特莉娜的在线玩家」
================================================================

这条【和踢人无关】，是另一个命令。

实查：全服只有一处发这句（MiscHandler.cpp:1067）：

    void WorldSession::HandleWhoIsOpcode(WorldPacket& recvData)     <- :1045
    {
        ...
        Player* player = ObjectAccessor::FindConnectedPlayerByName(charname);
        if (!player)
        {
            SendNotification(LANG_PLAYER_NOT_EXIST_OR_OFFLINE, charname.c_str());  <- :1067
            return;
        }

【HandleWhoIsOpcode 就是 /whois 命令。】

----------------------------------------------------------------
 这条线索价值很大
----------------------------------------------------------------

有个东西在对队友执行 /whois。

    /whois 是【纯客户端发起】的命令，
    服务端代码里没有任何地方主动调它。

    我们的 pbot 代码也从没发过这个包。

所以：【确定是你的客户端插件】。

它在做的事很典型：

    遍历队伍成员
      -> 先 /whois 查这个人的账号信息
      -> 再尝试踢掉（uninvite）

"卡特莉娜"是你某个 pbot 的角色名吧？
插件查它时，`FindConnectedPlayerByName` 找不到 ——
因为 pbot 的会话没有真实 socket，
在某些"在线玩家"索引里不算数。

----------------------------------------------------------------
 两个选择
----------------------------------------------------------------

A) 找出并关掉那个插件（推荐，治本）

    D:\WOW\Interface\AddOns 改名成 AddOns_bak
    重进游戏，组队 pbot，看还刷不刷

    不刷了 -> 一个个开回来，找出是哪个
    常见嫌疑：队伍管理类、自动整理队伍、GearScore 之类会查队友信息的

B) 服务端也把 whois 静默掉（治标）

    文件 MiscHandler.cpp，搜索 :1065-1069：

        if (!player)
        {
            SendNotification(LANG_PLAYER_NOT_EXIST_OR_OFFLINE, charname.c_str());
            return;
        }

    替换为：

        if (!player)
        {
            // F30: 不回这个包。插件会对 pbot 执行 /whois，
            // pbot 没有真实连接，FindConnectedPlayerByName 查不到，
            // 每次都回一句提示 -> 刷屏。
            return;
        }

    风险：你自己手动 /whois 一个不存在的人时，也不会有提示了。
    影响很小。

================================================================
 问题3：上线后队长还是鲤鱼
================================================================

【这不是钩子被占用，是队长信息本来就存在数据库里。】

队伍是持久化的（groups 表），队长是其中一个字段。
你下线前把队长转给自己了，但——

    如果【bot 比你后下线】，或者【bot 先上线】，
    服务端加载队伍时可能重新指定队长。

更常见的情况是：

    你下线 -> 队伍里只剩 bot -> 服务端自动把队长给了唯一在线的成员（bot）
    -> 这个变更被存进了 groups 表
    -> 你再上线，队长就是 bot 了

----------------------------------------------------------------
 A40 改动一为什么没挡住
----------------------------------------------------------------

A40 的让队长逻辑在 TryAcceptGroup 里 ——
【只在 bot 接受组队邀请那一刻执行一次】。

上线时队伍是从数据库恢复的，不走 TryAcceptGroup，
所以不会触发让队长。

----------------------------------------------------------------
 修法：每次 OnUpdate 都检查一次
----------------------------------------------------------------

文件 pbot_autoaccept.cpp

在 OnUpdate 的循环里，搜索：

            if (e.AutoFlags & PBOT_AUTO_GROUP)      TryAcceptGroup(bot);

在它【上面】插入：

            // F30: bot 不该当队长。
            // A40 只在接受邀请时让一次，但队伍是持久化的
            // （groups 表存了队长），重新登录后会恢复成 bot 当队长。
            // 所以每次巡检都确认一遍。
            if (Group* pgrp = bot->GetGroup())
            {
                if (pgrp->IsLeader(bot->GetGUID()))
                {
                    for (GroupReference* itr = pgrp->GetFirstMember(); itr != nullptr; itr = itr->next())
                    {
                        Player* mem = itr->GetSource();
                        if (mem && mem != bot && mem->IsInWorld() &&
                            mem->GetSession() && !mem->GetSession()->PlayerDisconnected())
                        {
                            pgrp->ChangeLeader(mem->GetGUID());
                            break;
                        }
                    }
                }
            }

这样只要队伍里有【真人】在线，队长就会自动转给他。

需要的 API（已实查）：

    Group.h:211  ChangeLeader(ObjectGuid)              public(185段)
    Group.h:240  IsLeader(ObjectGuid) const            public(185段)
    Group.h     GetFirstMember()                       public
    WorldSession.h:503  PlayerDisconnected()           public

================================================================
 问题4：公会签名还是灰的
================================================================

A40 改动二可能没生效，或者装的位置不对。

先自查：

    PetitionsHandler.cpp 里 Ctrl+F 搜 PlayerDisconnected
    应该有 1 个结果，在 HandleOfferPetitionOpcode 里面

如果是 0 个，说明改动二没装上。

如果有 1 个，加个日志确认它被执行到：

在你加的那段 if 前面插入：

    TC_LOG_ERROR("misc", "[F30] OfferPetition: 目标={} Disconnected={}",
        player->GetName(), uint32(player->GetSession() ?
        player->GetSession()->PlayerDisconnected() : 0));

然后重新点一次"要求签名"，看 Server.log：

    没有 [F30] 日志
        -> 钩子代码没编译进去，或位置不对

    Disconnected=0
        -> pbot 的 m_Socket 不为空，判断条件失效
        -> 改用 IsBotSession() 或两个都判

    Disconnected=1 但还是灰的
        -> 签名成功了但客户端没收到结果包
        -> 需要检查 SMSG_PETITION_SIGN_RESULTS 那段
