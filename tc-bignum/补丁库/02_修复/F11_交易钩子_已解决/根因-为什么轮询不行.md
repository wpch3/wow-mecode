## 二、轮询为什么不可靠 —— 三个致命时序问题

### 2.1 问题1：`_pbotTradeOpened` 这个集合会卡死

我用一个 `std::set` 记「已经给谁开过窗口」，防止每秒重复发包：

```cpp
// pbot_autoaccept.cpp
static std::set<ObjectGuid> _pbotTradeOpened;

if (_pbotTradeOpened.count(bot->GetGUID()))
    return;                                  // <- 已开过，直接返回
_pbotTradeOpened.insert(bot->GetGUID());
```

**清理只发生在 `trade == nullptr` 的时候**。

问题来了：如果**第一次开窗失败了**（任何原因），
`_pbotTradeOpened` 里已经有这个 bot 了，而 `m_trade` 还挂着
（非空，不触发清理）——

**从此以后，这个 bot 的交易【永远不会再被处理】。**

你重登也没用，因为 `_pbotTradeOpened` 是**进程级静态变量**，
只有重启服务器才清。

> **这极可能就是你现在的状态**：某次失败后集合被污染，
> 之后不管怎么改开关、怎么重开 bot 都没反应。

### 2.2 问题2：`g_pbots` 是纯内存的，重启就空

```cpp
// cs_playerbot.cpp:106
std::vector<PBotEntry> g_pbots;
```

轮询只遍历 `g_pbots`。服务器重启后这个表是空的，
**即使 bot 还在线（角色在数据库里），也不在表里 -> 永远轮不到它。**

如果你中间重启过服务器而没重新 `.pbot spawn`，交易就不可能工作。

### 2.3 问题3：1秒的窗口期，客户端可能已经放弃

```cpp
static constexpr uint32 CHECK_INTERVAL = 1000;   // 1秒才扫一次
```

你点交易 -> 最坏情况 1 秒后 bot 才"接受" -> 客户端可能已经超时。

**三个问题叠加，轮询这条路的成功率本来就不高。**

## 三、新方案：在核心里钩住，零延迟零状态

### 3.1 插入点（实查确认）

`TradeHandler.cpp:723-729`，`HandleInitiateTradeOpcode` 的**最后三行**：

```cpp
    // OK start trade
    _player->m_trade = new TradeData(_player, pOther);
    pOther->m_trade = new TradeData(pOther, _player);

    info.Status = TRADE_STATUS_BEGIN_TRADE;
    info.TraderGuid = _player->GetGUID();
    pOther->GetSession()->SendTradeStatus(info);    // <- 给bot发，bot收不到
}                                                    // <- 【在这之前插入】
```

**在这里插入的好处**：

| | 轮询 | 核心钩子 |
|---|---|---|
| 时机 | 最坏延迟 1 秒 | **同一个函数调用内，零延迟** |
| 依赖 `g_pbots` | **是**（重启失效） | **否** |
| 依赖 `_pbotTradeOpened` | **是**（会卡死） | **否** |
| 依赖开关配置 | **是** | **否** |
| 能否失败 | 有多个失败点 | **只要交易建立了就一定执行** |

### 3.2 要插入的代码（10行）

```cpp
    // OK start trade
    _player->m_trade = new TradeData(_player, pOther);
    pOther->m_trade = new TradeData(pOther, _player);

    info.Status = TRADE_STATUS_BEGIN_TRADE;
    info.TraderGuid = _player->GetGUID();
    pOther->GetSession()->SendTradeStatus(info);

    // ===== step57: PlayerBot 自动接受交易 =====
    // bot 没有客户端，收不到上面那个 BEGIN_TRADE，
    // 也就永远不会发 CMSG_BEGIN_TRADE 回来。
    // 而【真正打开双方窗口的是 OPEN_WINDOW】(本文件 :584-586)，
    // 它只在 HandleBeginTradeOpcode 里发。
    // -> 不替 bot 走这一步，发起方的窗口永远不会打开。
    if (pOther->GetSession()->IsBotSession())
    {
        WorldPacket dummy(CMSG_BEGIN_TRADE, 0);
        pOther->GetSession()->HandleBeginTradeOpcode(dummy);
    }
}
```

### 3.3 为什么这次一定行

**判断条件 `IsBotSession()` 是你自己在 step40 加的**
（`WorldSession.h`，`AddLegitCharacter` 旁边）：

```cpp
void SetBotSession(bool val) { m_isBotSession = val; }
bool IsBotSession() const { return m_isBotSession; }
```

而 `cs_playerbot.cpp:280` 每个 bot spawn 时都会设：

```cpp
sess->SetBotSession(true);
```

**这个标记的生命周期 = 会话的生命周期**，
不依赖任何我自己维护的表，不会失步。

**执行路径**：

```
你右键bot->交易
  -> HandleInitiateTradeOpcode
  -> 层层检查全过（距离/阵营/存活...）
  -> :724  双方 m_trade 建立
  -> :729  给bot发BEGIN_TRADE（丢弃，无所谓）
  -> 【新】发现是bot -> 直接调 HandleBeginTradeOpcode
     -> :584  给trader(=你)发 OPEN_WINDOW    <- 你的窗口打开
     -> :585  给自己(bot)发 OPEN_WINDOW      <- 丢弃，无所谓
  -> 你看到交易窗口
```

**同一个函数调用栈内完成，没有任何时序问题。**

### 3.4 安全性

- `HandleBeginTradeOpcode` 内部第一件事是 `if (!my_trade) return;`
  —— 而我们刚在上面两行建立了 `m_trade`，**必定非空**
- 参数在官方实现里就是注释掉的（`WorldPacket& /*recvPacket*/`），
  空包安全
- 只影响 `IsBotSession()` 为真的会话，**真人玩家零影响**
- **不调 `HandleAcceptTradeOpcode`** —— 最终确认永远你自己点

## 四、同时清理轮询版本（避免两套打架）

`pbot_autoaccept.cpp` 里的 `TryAcceptTrade` **要停用**。

理由：核心钩子已经在交易建立那一刻处理完了，
轮询再跑一遍会**重复发 OPEN_WINDOW**，可能反而搞乱状态。

但**距离自愈要保留**（那个是钩子做不到的，需要持续监控）。

所以 `TryAcceptTrade` 改成 **只做距离检查，不再开窗口**。

## 五、party1 刷屏 —— 这次直接根治

### 5.1 复述根因

「party1不在你的队伍中」= `ERR_TARGET_NOT_IN_GROUP_S`，
全服只有两处发（`GroupHandler.cpp:335` / `:381`），**都是踢人函数**。

`party1` 是客户端的**单位ID**，不是名字。服务端拿它按名字找人
（`Group.cpp:2854`），永远找不到 -> 回一句"不在你的队伍中"。

### 5.2 为什么客户端会发这个

3.3.5 客户端在**队伍成员是"非常规单位"**时，某些 UI 操作会
直接把 UnitID 当名字发上来。**NPCBot 是 Creature 冒充队伍成员**，
正好触发这个路径。

**这解释了为什么你只在组 npcbot 时遇到，组真人不会。**

### 5.3 修法：识别保留字，静默忽略

在两个 handler 里各加一个判断。

**判断逻辑**（覆盖所有客户端保留 UnitID）：

```
party1-party4          队伍成员
raid1-raid40           团队成员
partypet1-4 / raidpet* 队友的宠物
player / target / focus / pet / mouseover / none
arena1-5 / boss1-4
```

统一规则：**以这些前缀开头 + 后面全是数字**，或者完全等于这些词。

### 5.4 为什么是"静默"而不是"回个正确的错误"

因为**这个请求本身就是客户端发错的**，不是你的操作。

回任何包都会在聊天栏留一行字。**直接 return 什么都不回**，
客户端不会重试（它本来也不期待回应），刷屏就停了。
