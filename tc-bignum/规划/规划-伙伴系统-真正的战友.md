## 一、【推翻我自己】"做不到"的三条，重新审视

我之前说过三个"做不到"。按新铁律重新过一遍：

### 我说过：「bot 是 Creature，不能做 Player 的事」

**这句话作为技术描述是对的，但作为结论是错的。**

因为——**bot 根本不需要"成为 Player"才能给你东西。**

实查源码，`bot_ai.cpp:8467-8483`（术士给玩家治疗石）：

```cpp
ItemPosCountVec dest;
InventoryResult msg = player->CanStoreNewItem(NULL_BAG, NULL_SLOT, dest, HealthStones[i], 1);
if (msg != EQUIP_ERR_OK)
{
    player->SendEquipError(msg, nullptr, nullptr, HealthStones[i]);
    break;
}
Item* item = player->StoreNewItem(dest, HealthStones[i], true, 0);
player->SendNewItem(item, 1, true, false, true);
```

**这段代码已经在跑了。** bot 给玩家物品的完整链路——
检查背包空间、创建物品、发送提示——**全部现成**。

还有更直接的：

```cpp
bot_ai.cpp:4771    receiver->AddItem(32408, 1);   // Naj'entus Spine
bot_ai.cpp:4947    receiver->AddItem(50307, 1);   // Infernal Spear
```

**`AddItem` 一行就能给。** 上游作者自己就在用。

### 我说过：「bot 不能自己接任务」

**这条技术上仍然成立**（QuestMgr 要 `Player*`），
**但它和你的需求无关。** 一个好战友不需要会交任务，
需要的是**在你没钱的时候塞给你几个金币**。

### 我说过：「有主人就关闭自主行为」

`bot_ai.cpp:4414` 的 `IAmFree()` 确实挡住了游荡移动。
**但那只挡"移动"，不挡"给予"、"说话"、"观察"。**

**我把一个局部约束，错误地推广成了全局限制。**
这正是我犯过 8 次的同一个错误。

## 二、【关键结论】你要的功能，底层零阻碍

把需求逐条对照源码：

| 你要的 | 需要什么能力 | 源码现状 |
|---|---|---|
| 你饿了给你面包 | ① 感知玩家状态 ② 给物品 | **都有** |
| 你渴了给你水 | 同上 | **都有** |
| 你穷了给你钱 | ① 读玩家金钱 ② 给钱 | **都有** |
| 分享见闻趣事 | 私聊 + 触发条件 | **都有** |
| 从自己包里拿 | bot 物品栏 | **有**（`_equips` / GearBank）|

## 三、伙伴系统设计

### 核心思想：bot 有"关注玩家"的循环

```cpp
// 每 N 秒跑一次
void bot_ai::UpdateCompanionCare(uint32 diff)
{
    if (!master || IAmFree()) return;
    if (me->IsInCombat() || master->IsInCombat()) return;   // 打架时不啰嗦
    if (_careCooldown > diff) { _careCooldown -= diff; return; }

    // 按优先级检查玩家状态
    if (TryOfferFood())      return;   // 饿了
    if (TryOfferDrink())     return;   // 渴了
    if (TryOfferMoney())     return;   // 穷了
    if (TryOfferItem())      return;   // 有用得上的东西
    if (TryShareStory())     return;   // 没事，聊两句
}
```

### 关怀条目表（可扩展）

| 触发条件 | bot 行为 | 台词示例 |
|---|---|---|
| 玩家血量 < 50% 且脱战 | 递食物 | 「先垫垫肚子，脸都白了。」 |
| 玩家法力 < 40% 且脱战 | 递水 | 「喝点水，别硬撑。」 |
| 玩家金钱 < 阈值 | 给钱 | 「拿着，我路上捡的。」 |
| 玩家装备有空位 | 给对应装备 | 「这个你能用，我留着也是压箱底。」 |
| 玩家死亡后复活 | 关心 + 给增益 | 「吓死我了，慢点走。」 |
| 玩家升级 | 祝贺 | 「越来越像样了。」 |
| 长时间无事 | 讲见闻 | 「上次我在这附近见过一头白鹿……」 |
| 进入新区域 | 讲当地故事 | 「这地方我熟，前面山口有埋伏。」 |
| 打完硬仗 | 感慨 | 「刚才那下真险。」 |
| 玩家背包满 | 提醒 | 「你包满了，要我帮你拿点吗？」 |

**「也不止于此」—— 这张表就是留给你不断加的。**

### 关键设计原则（避免变成骚扰）

| 原则 | 做法 |
|---|---|
| **不刷屏** | 全局冷却（如 60 秒），每类单独冷却 |
| **不重复** | 同一句话不连着说，台词池随机 |
| **看场合** | 战斗中只说要紧的，脱战才闲聊 |
| **可关闭** | conf 开关 + Gossip 里能单独关"话痨" |
| **有性格** | 不同职业/身份说话风格不同 |

### 和身份体系联动

```
剧情bot    -> 说剧情相关的见闻，推进氛围
偶遇同伴   -> 说自己的来历、想去的地方
普通雇佣bot -> 说职业相关的话
玩家bot    -> 像真玩家一样闲聊
```

## 四、"从自己背包里拿" —— 这条最有味道

你特别强调了「**会自己拿出背包里的东西**」。这和"凭空变出来"是两回事。

### 现状

bot 有装备栏（`_equips[]`）和 GearBank（`BotCfg::IsGearBankEnabled()`），
**但没有真正意义上的"背包"**。

### 三种实现（推荐第 2 种）

**方案 1：凭空生成（最简单，但没味道）**
```cpp
player->AddItem(ITEM_BREAD, 1);   // 直接给
```
**缺点**：不符合"从背包拿"的设定，也可能被刷。

**方案 2：bot 虚拟背包（推荐）**
```
新表：characters_npcbot_inventory
      bot_guid | item_id | count | acquired_from

来源：
  - bot 自动拾取时，一部分进它自己的包（现有 AUTOLOOT 已经在捡）
  - 出生时按职业/身份给初始物品（法师带面包，猎人带肉干）
  - 任务/剧情奖励

给予：
  从包里扣，给玩家。包空了就没得给。
```
**优点**：
- **有物理来源**，不是凭空
- bot 捡的东西真的会用在你身上 —— **这才是"战友"**
- 可以做"bot 的包里有什么"的查看界面

**方案 3：从 GearBank 拿（半成品）**
GearBank 是给装备用的，塞消耗品不太合适。

### 关键细节：给了要说清楚从哪来的

```
「这面包是我在南海镇买的，你先吃。」
「刚才那只狼身上掉的，你拿着。」
「我攒的，反正我也不花钱。」
```

**物品来源写进台词** —— 这是"真实感"的关键，
而 `acquired_from` 字段就是为此准备的。

## 五、至今为止我们做得不够好的地方

按你的要求，反思一下。

### 5.1 我反复犯的错：把"约束"当"边界"

**8 次同类错误，本质都是一个**：

```
发现一个限制 -> 停止思考 -> 宣布"做不到"
```

而正确的做法是：

```
发现一个限制 -> 问"这个限制挡住的到底是什么" -> 找绕过的路
```

**具体到这次**：
- 「bot 是 Creature 不是 Player」 -> 挡住的只是**任务系统**，不挡给予和对话
- 「IAmFree 关闭自主行为」 -> 挡住的只是**移动**，不挡关怀逻辑
- 「MultiConverter 不支持 .skel」 -> 挡住的只是**那一个工具**

**新的自检问题**：每次我说"做不到"之前，必须回答：
1. 这个限制**具体**挡住了哪个函数/哪条路径？
2. 绕过它需要什么？（不是"能不能"，是"需要什么"）
3. 有没有**不经过这条路**的其他实现？

### 5.2 做完的东西缺少"串起来"

我们有 33 个 step，但它们像**一堆零件**：

```
.scene .nst .emote .say    剧情工具（GM 手动用）
.disguise .model .fm       外观工具（GM 手动用）
NPCBot                     独立系统
真龙剧情文档               还没落地成游戏内容
```

**没有一个东西把它们连起来。**

**伙伴系统恰好是那个连接点**：
- bot 说话 -> 用 `.say` 的语气/表情系统
- bot 演出 -> 用 `.emote` 的动作库
- bot 剧情 -> 用 `.scene` 的场景快照
- bot 身份 -> 接真龙剧情的七位凡人主角

**建议：把伙伴系统当成"总集成"来做**，而不是又一个孤立功能。

### 5.3 缺"玩家视角"的验收

我们所有验证都是「指令能不能跑通」，
**没有一次是「玩起来什么感觉」**。

比如 `.emote` 82 项测试全过，但从来没问过：
「用这套工具做一段 5 分钟的剧情，观感如何？」

**建议**：每完成一个系统，做一次**5 分钟的实际内容**当验收。
伙伴系统就该这么验——**带一个 bot 玩半小时，看它像不像个人。**

### 5.4 数值/内容的"配置化"不足

现在很多东西写死在代码里（台词、阈值、概率）。
**伙伴系统如果也写死，以后每改一句话都要重编译。**

**建议**：
```
台词        -> 数据库表（可热重载，支持多语言）
触发阈值    -> conf
概率/冷却   -> conf
关怀条目    -> 数据表驱动，加一条不用改代码
```

**这样你可以自己不断往里加内容，不用等我。**

### 5.5 还能做什么（新想到的）

| 想法 | 说明 |
|---|---|
| **bot 记忆** | 记住和你一起打过的BOSS、去过的地方，以后提起 |
| **bot 情绪** | 连续死亡会沮丧，连胜会兴奋，影响台词 |
| **bot 关系** | 多个 bot 之间互相说话、拌嘴 |
| **bot 成长故事** | 从菜鸟到老兵，台词随等级变化 |
| **bot 请求** | 它也会求你："能给我把好点的剑吗？" |
| **告别** | 剧情 bot 离队时有正式的告别 |
| **重逢** | 之前的同伴再遇到会认出你 |

**这些全部只需要"数据 + 触发逻辑"，没有一个撞引擎墙。**
