## 二、「补货很慢」——这是**正常的**，原因在源码里

### 真相：你的拍卖行已经 99.5% 满了，没多少可补

实查 `AuctionHouseBotSeller.cpp:952-960`：

```cpp
// If there is large amount of items missed we can use boost value to get fast filled AH
if (config.LastMissedItem > sAuctionBotConfig->GetItemPerCycleBoost())
{
    items = sAuctionBotConfig->GetItemPerCycleBoost();     // 补 5000
}
else
    items = sAuctionBotConfig->GetItemPerCycleNormal();    // 补 500   <- 你在这一档
```

**算给你看**：

```
单行目标 39700，你已有 39498   ->  缺口只有 202
202 < Boost阈值 5000            ->  走 else 分支，每周期最多补 500
而实际只补 202 件就满了         ->  剩下的 298 个名额根本用不上
```

**所以不是补得慢，是没东西可补了。** 每 60 秒它只需要补掉"刚过期下架"的那一小部分。

### `ItemsPerCycle.Boost = 5000` 什么时候才生效

只有**缺口 > 5000** 时才走 Boost 分支。触发场景：

```
· .ahbot rebuild all 之后（大量挂单被标记过期）
· 你刚改完 Class.Misc，配额重新分配，某些类别缺口突然变大
```

**你现在改了 `Class.Misc = 2`，等于给"其他类别"腾出了配额**，
下一轮 rebuild 后缺口会变大，那时 Boost 就会启动，补货会明显变快。

### 「六十秒补货」的实际含义

`Update.Interval = 60` 是**每个行各自 60 秒跑一次**（`Update(houseType)` 按行调用），
三个行合计理论上最多 `3 × 5000 = 15000 件/分钟`（Boost 档）
或 `3 × 500 = 1500 件/分钟`（Normal 档）。

**你等 20 分钟再看是对的。** 但如果拍卖行已经满了，等再久数字也不会涨——
因为 `.ahbot status` 显示的就是"当前/目标"，满了就停在那。

## 三、你把 `Class.Misc` 改成 2 —— 这个决定我支持，但有个副作用要知道

### 支持的理由

你实测「坐骑太多了」，那就是配额过剩，调低正确。**你的判断优先于我的推算。**

### 但必须告诉你一个连带效果（权重是相对的）

```
Misc=8: 权重总和 64
Misc=2: 权重总和 58      <- 分母变小了
```

**分母一小，其他所有类别的配额都会上升**：

| 类别 | Misc=8 时 | Misc=2 时 | 变化 |
|---|---|---|---|
| TradeGood（材料） | 6203 | **6845** | +642 |
| Weapon（武器） | 4962 | **5476** | +513 |
| Armor（护甲） | 4962 | **5476** | +513 |
| Consumable（消耗品） | 3722 | **4107** | +385 |
| **Misc（坐骑所在）** | 4962 | **1369** | **-3593** |

**这是好事**：你少了坐骑，多了材料和装备，总量不变。
**也解释了你的另一个观察**——改完之后其他货物的目标数量变高了，
所以短期内会显得"还没补满"。**这正是需要等 20 分钟的原因。**

## 四、建议：等这一轮铺完再判断

```
1. 确认 ahbot.conf 里 Class.Misc = 2 已保存
2. .reload config
3. .ahbot reload
4. .ahbot rebuild all        <- 关键，让新配额生效
5. 等 20 分钟
6. .ahbot status             <- 看"当前/目标"是不是都接近
```

### 20 分钟后如果还觉得慢，跑这条看真实缺口

```sql
SELECT
    CASE it.`class`
        WHEN 2  THEN '武器'
        WHEN 4  THEN '护甲'
        WHEN 7  THEN '材料'
        WHEN 0  THEN '消耗品'
        WHEN 15 THEN '杂项(含坐骑)'
        ELSE CONCAT('class=', it.`class`)
    END AS `类别`,
    COUNT(*) AS `当前挂单数`
FROM `characters`.`auctionhouse` a
JOIN `characters`.`item_instance` ii ON ii.`guid` = a.`itemguid`
JOIN `world`.`item_template` it      ON it.`entry` = ii.`itemEntry`
GROUP BY it.`class`
ORDER BY `当前挂单数` DESC;
```

把结果贴我，我能算出每个类别离目标还差多少。

## 五、坐骑白名单（09号方案B）还要不要做？

**看你的取舍**：

| 你想要 | 怎么做 |
|---|---|
| 坐骑**种类多**但**数量少** | 做 09 号白名单（295种进池）+ 保持 `Class.Misc = 2` |
| 坐骑就现在这样（3 种） | 不做 09 号，保持现状 |

**注意**：你说的"坐骑太多"是**数量**多（143 个挂单里全是那 3 种在刷屏），
而 09 号解决的是**种类**少。两者不冲突——
`Class.Misc=2` 控制总量，白名单控制花色。**一起用效果最好：种类多了，每种少几个。**
