## 嫌疑1：台词表是空的（最可能，先查这个）

`PickRequestText` 返回 nullptr 时，函数**静默返回**，什么都不说：

```cpp
CompanionRequestText const* rt = sBotCompanionMgr->PickRequestText(reqType, tier, 0);
if (!rt)
{
    timer = 120000;
    return;          // <- 没台词就闭嘴，不报错
}
```

### 立刻验证

```sql
SELECT COUNT(*) AS `应该是17` FROM `world`.`npcbot_request_text`;
```

同时看**启动日志**里有没有这行：

```text
>> Loaded 17 npcbot request texts in X ms
```

| 结果 | 说明 |
|---|---|
| SQL 是 17，日志也有 | 表没问题，看嫌疑2 |
| SQL 是 17，**日志没有** | `LoadRequestTexts()` 没接进 `ReloadAll()` |
| SQL 是 0 | 第1步 SQL 没跑，或被后来的 SQL 覆盖了 |

### 如果 SQL 是 0，重新灌数据

跑 `补丁库/01_功能/A37_羁绊与关怀_双向重做/sql/01_双向数据层.sql`
里的 `npcbot_request_text` 那段 INSERT。

## 嫌疑2：`_lastRequestType` 防重复把它卡住了

```cpp
uint8& lastReq = _pbotLastRequest[bguid];
if (reqType == lastReq && urand(0, 2))
{
    timer = 60000;
    return;
}
```

`_pbotLastRequest[bguid]` 对新 key **默认构造出 0**，
而 `BOT_REQUEST_NONE` 也是 **0**。

**所以第一次判定出 reqType 时**：

```text
reqType = 1 (食物)
lastReq = 0 (默认值)
1 == 0 为假 -> 不会卡住
```

这一次是安全的。但如果它**说过一次食物**之后，
`lastReq` 变成 1，后面连续要食物时就有 2/3 概率被跳过，
每次跳过再等 60 秒 —— **看起来就像不说话**。

### 判断方法

```sql
SELECT * FROM `characters`.`npcbot_request_log`
WHERE bot_kind = 1 ORDER BY id DESC LIMIT 5;
```

| 结果 | 说明 |
|---|---|
| **有记录** | 它说过话，只是你没注意到（消息在聊天框滚过去了）|
| **空的** | 从没说过，是嫌疑1 或前面的门槛 |

## 一个容易忽略的点：消息在哪显示

第6步用的是：

```cpp
ChatHandler(owner->GetSession()).PSendSysMessage(
    "|cffffff00[%s]|r %s", bot->GetName().c_str(), rt->Text.c_str());
```

**这是系统消息，显示在【常规聊天框】**，不是私聊窗口，
也不会有提示音。战斗刷屏时很容易滚过去。

### 建议

先把聊天框其它频道关掉，只留"系统"，再测试。

## 顺带：等待时间可能比你想的长

```text
bot 上线      -> 首次登记 60-120 秒延迟（修复4加的）
无需求时      -> 每 30 秒查一次
判定有需求    -> 立刻说
说完之后      -> 冷却 tier 相关：
                 生疏(tier1)  6-10 分钟
                 熟悉(tier2)  3-5 分钟
                 深交(tier3)  1.5-2.5 分钟
```

**你的 bot 大概率是 tier1（生疏）** —— 因为羁绊分还是 0。
所以第一次说完后，要等 6-10 分钟才会说第二次。

### 想快速测试就手动改羁绊

```sql
UPDATE `characters`.`npcbot_bond`
SET gift_points = 2000, bond_points = 2000, bond_level = 5
WHERE bot_kind = 1;
```

改完 tier=3，冷却缩短到 1.5-2.5 分钟。
