【先回答你的问题:能不能改上限?】

答案分两半,必须分清:

================================================================================
第零部 · 上限的真相
================================================================================

■ 有两个完全不同的"上限",很多人会混淆

【上限A】种族/职业 ID 本身
    字段: uint8 Race / uint8 Class   (CharacterPackets.h:34-35)
    范围: 0 ~ 255
    结论: ID 可以编到 255,这个不是瓶颈

【上限B】位掩码 racemask / classmask   * 真正的瓶颈
    字段: uint32                     (ItemTemplate.h:615-616)
                                     (DBCStructure.h:1333-1334)
    算法: 1 << (ID - 1)

    实测:
      ID=30 -> 1<<29 = 536,870,912      [OK]
      ID=32 -> 1<<31 = 2,147,483,648    [OK]  <- 极限
      ID=33 -> 1<<32 = 4,294,967,296    [溢出!]

    结论: 硬上限 = 32 个种族 / 32 个职业

■ 能不能突破 32?

  服务端: 可以。把 uint32 改成 uint64,再改几十处相关代码。
  客户端: 【不建议】。原因有三:
      1. racemask 在客户端 DBC 里也是 uint32
      2. 客户端 exe 内部按 32 位解析这些掩码
      3. 突破需要逆向修改 exe 二进制,风险极高且每次客户端更新都要重做

■ 但是 —— 你根本不需要突破

    你的需求: 种族 20~30 个,职业 20 个
    可用额度: 种族 32 个,职业 32 个

    完全在范围内。而且 32 这个数字,已经比正式版魔兽的
    (10种族 / 10职业) 多出两倍还多。

    下面的规划就按 32 上限来做,把每一个槽位都用好。

第三部 · 种族 x 职业 可选矩阵原则
================================================================================

■ 设计原则

  1. 不要所有种族都能选所有职业 —— 限制创造特色
  2. 每个新职业至少 4-6 个种族可选 —— 保证不冷门
  3. 每个种族至少 5-8 个职业可选 —— 保证不单调
  4. 高等精灵是唯一"全职业"种族 —— 呼应他们"完整"的设定
  5. 真龙只能选龙裔 —— 但龙裔能用所有职业的技能

■ 特殊规则

  · 真龙(12) 只能选 龙裔(12)
  · 龙裔(12) 只有 真龙(12) 能选
  · 高等精灵(16) 可选全部职业(设定呼应)
  · 断链武僧(13) 几乎所有种族可选(奴隶出身,不分种族)

■ 6-1 服务端 C++ 改动(9 处硬编码)

MAX_RACES / MAX_CLASSES 是**定长数组维度**,不是简单的上限值。
改大之后,所有按这个维度声明的数组都要补齐数据,
少补一个就是启动崩溃或者属性全 0。

  【第 0 处】SharedDefines.h —— 枚举与维度
      enum Races  加 RACE_DRAGONSWORN = 12
      enum Classes 加 CLASS_DRAGONSWORN = 12
      #define MAX_RACES   12  ->  改成你要的数(如 33)
      #define MAX_CLASSES 12  ->  同上

      注意:这两个宏要比最大 ID 大 1(因为下标从 0 开始)

  【必补的 9 处数组初始化】
  ┌───┬──────────────────────────┬────────────────────────────┐
  │ # │ 文件:行号                │ 内容                        │
  ├───┼──────────────────────────┼────────────────────────────┤
  │ 1 │ ObjectMgr.h:1670         │ 种族-职业 组合表            │
  │ 2 │ StatSystem.cpp:690       │ 基础属性表                  │
  │ 3 │ StatSystem.cpp:728       │ 护甲计算表                  │
  │ 4 │ StatSystem.cpp:754       │ 攻击强度表                  │
  │ 5 │ StatSystem.cpp:796       │ 法术强度表                  │
  │ 6 │ Player.cpp:5249          │ 职业相关初始化              │
  │ 7 │ Player.cpp:5264          │ 同上(第二处)                │
  │ 8 │ CommonHelpers.cpp:189    │ 职业->主属性 映射           │
  │ 9 │ spell_item.cpp:318       │ 物品法术的职业分支          │
  └───┴──────────────────────────┴────────────────────────────┘

  【位掩码上限提醒】
      AllowableClass / AllowableRace 是 uint32   (ItemTemplate.h:615-616)
      RaceMask / ClassMask 也是 uint32           (DBCStructure.h:1333-1334)
      算法都是 1 << (ID - 1)

      ID = 32 -> 1<<31 = 2147483648  [还行]
      ID = 33 -> 溢出                [炸]

      所以 32 是硬上限。你规划的 32 种族 + 23 职业正好卡在线内,
      不需要动这个。

■ 6-2 数据库改动(6 张表)

按你 SQL 客户端的脾气,每张表一个文件,一个文件一条语句,
不带反引号写 `库.表`。

  【1】world.playercreateinfo —— 出生点
      INSERT INTO world.playercreateinfo
        (race, class, map, zone, position_x, position_y, position_z, orientation)
      VALUES (12, 12, 1, 14, -2917.58, -257.98, 52.9, 0);
      （地图 1 = 卡利姆多,这里填无名山谷的坐标）

  【2】world.playercreateinfo_item —— 初始装备
      每件一行,race + class + itemid + amount

  【3】world.playercreateinfo_spell_custom —— 初始技能
      至少要有:该种族的语言技能、基础武器技能

  【4】world.playercreateinfo_action —— 初始动作条

  【5】world.playercreateinfo_skills —— 初始技能线
      **这张表最容易漏**。漏了的后果是不能说话、不能穿装备。

  【6】world.player_levelstats + player_classlevelstats —— 每级属性
      这是量最大的:每个种族 x 每个职业 x 每一级 一行。
      80 级的话 = 80 行/组合。
      建议写脚本从现有种族复制后批量改 race/class 字段。

      SQL 思路(以复制血精灵 race=10 的数据给真龙 race=12 为例):
          INSERT INTO world.player_levelstats
            (race, class, level, str, agi, sta, inte, spi)
          SELECT 12, class, level, str, agi, sta, inte, spi
          FROM world.player_levelstats WHERE race = 10;

      这一条就能生成全部数据,比手填快一万倍。

■ 6-3 客户端 DBC 改动(必改 8 个)

这部分是客户端补丁(打进 MPQ),漏一个就崩。

  ┌──────────────────────────┬──────────────────────────────────┐
  │ ChrRaces.dbc             │ 种族本体。名称/模型/派系          │
  │ ChrClasses.dbc           │ 职业本体(加新职业时)              │
  │ CharBaseInfo.dbc         │ 种族-职业 可选组合                │
  │ CharStartOutfit.dbc      │ 初始外观装备                      │

  │ SkillLineAbility.dbc     │ 技能可学列表  **漏了不能说话**    │
  │ SkillRaceClassInfo.dbc   │ 种族可学技能  **漏了不能穿装备**  │
  │ gt*.dbc (11 个)          │ 属性成长曲线  **漏了崩天赋面板**  │
  └──────────────────────────┴──────────────────────────────────┘

  【gt 系列的 11 个文件】(这组最容易被忽略)
      gtCombatRatings.dbc
      gtChanceToMeleeCritBase.dbc
      gtChanceToMeleeCrit.dbc
      gtChanceToSpellCritBase.dbc
      gtChanceToSpellCrit.dbc
      gtOCTRegenHP.dbc
      gtOCTRegenMP.dbc
      gtRegenHPPerSpt.dbc
      gtRegenMPPerSpt.dbc
      gtOCTClassCombatRatingScalar.dbc
      gtBarberShopCostBase.dbc

      这些表的行数 = MAX_CLASSES x GT_MAX_LEVEL。
      加职业就要按新的 MAX_CLASSES 重新生成整个文件。

  【GT_MAX_LEVEL 的坑】
      DBCStructure.h:758  #define GT_MAX_LEVEL 100

      如果你以后要把等级上限提到 100 以上,
      这 11 个 gt 文件必须**全部重新生成**,
      否则超过 100 级的角色属性会读到越界数据。

■ 6-5 客户端崩溃点速查表

按"崩溃现象 -> 缺什么"倒查,省调试时间:

  ┌────────────────────────────┬──────────────────────────────┐

第七部 · 种族天赋的实装方式  【第二版新增】

■ 三种实现路径,按成本排序

  【路径一】纯 DBC 被动光环 —— 最省事
      适用:单纯的数值加成
      例:「岩石皮肤」物理减伤 5%

      做法:
        1. Spell.dbc 建一个被动法术
        2. SkillLineAbility.dbc 绑到种族
        3. playercreateinfo_spell_custom 里给初始技能
      不用写一行 C++。

  【路径二】SpellScript —— 中等成本
      适用:有条件判断的效果
      例:「为了孩子」队伍中有低于自己等级的成员时获得增益

      做法:
        src/server/scripts/Spells/spell_race_custom.cpp
        写一个 AuraScript,在 OnUpdate 里检查队伍情况

  【路径三】核心 Hook —— 高成本,慎用
      适用:改变基础规则的效果
      例:「存在锚定」免疫一切移除/放逐/相位类效果

      做法:改 Unit.cpp / SpellEffects.cpp 的对应分支
      风险:动核心代码,升级合并会冲突

■ 本作 32 个种族天赋的路径分配

  路径一(纯 DBC,占大多数):
      极寒适应 / 巨力 / 无畏 / 鳞甲 / 岩石皮肤 / 黑暗视觉 /
      夜行 / 双持精通 / 元素亲和 / 坚韧 / 完整之魂 /
      两百年 / 凝固思维 / 过滤者 ...

  路径二(SpellScript):
      为了孩子     队伍成员等级判定
      群狩         队伍人数判定
      见证者       附近同源种族判定
      畸变再生     随机变异效果
      燃烧余生     临时增益+永久代价
      晶化         致命伤害触发无敌
      十倍推演     暴击重置冷却
      冬眠         战斗中假死回血

  路径三(核心 Hook,只有这几个):
      存在锚定     免疫移除/放逐/相位   -> Unit::RemoveAura 分支
      天生失聪     免疫声音/魅惑类       -> Unit::IsImmunedToSpell
      无名者       免疫点名机制          -> 副本脚本层面处理
      影语         随机真假预言          -> 需要自定义 UI

  【建议】先把路径一的全做了,游戏就能玩起来。
  路径二边玩边加。路径三留到最后,或者用变通方案绕过去。

第八部 · 阵营归属与派系设计  【第二版新增】
================================================================================

■ 为什么要单独讲这个

剧情第二版的核心是「部落与联盟从对立到和解」,
这就带来一个技术问题:

    如果最终要和解,那新种族到底算哪边?

■ 三种阵营模式

  【模式一】固定阵营(传统做法)
      每个种族写死属于联盟或部落。
      ChrRaces.dbc 的 FactionID 字段决定。

      优点:简单,和现有系统完全兼容
      缺点:和剧情的和解主题冲突

  【模式二】中立种族(真龙用这个)
      真龙是绝对中立,两边都能接触。

      实现:
        FactionID 设为一个中立派系,
        然后用伪装系统(见《技能设计集》5-2 的【凡身】)
        让他能以任意阵营身份行动。

      这是本作真龙玩法的核心,必须做。

  【模式三】可切换阵营(和解后解锁)
      六卷《携手》签署《共同记得》之后,
      理论上双方可以互访。

      建议做法:**不做真正的阵营切换**(改动太大,容易出各种问题),
      改为:
        · 开放跨阵营组队(源血采集本来就需要)
        · 开放跨阵营聊天频道
        · 中立城市里双方 NPC 都不攻击
        · 保留各自的主城和阵营身份

      理由:和解不等于合并。剧情上双方仍是两个阵营,
      只是不打了。这样既贴合剧情,技术风险也最小。

■ 跨阵营组队的技术要点

  3.3.5 默认禁止跨阵营组队,需要改:
      · Group::AddMember 里的阵营检查
      · 聊天频道的阵营过滤
      · 副本进入时的阵营判定

  【重要】开了跨阵营组队之后,战场和竞技场要单独排除,
  否则会出现"自己人打自己人"的混乱。

  建议加一个开关,只在:
      · 源血采集区
      · PVE 副本
      · 中立地带
  这三种场景允许跨阵营组队。
