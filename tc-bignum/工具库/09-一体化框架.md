## 一、TSWoW

> 项目：https://github.com/tswow/tswow
> 定位：用 **TypeScript 写代码**来生成 WoW 内容（DBC + SQL + 脚本）

### 它解决什么问题

传统魔改流程：
```
手动改 DBC  +  手动写 SQL  +  手动打 MPQ  +  手动改 C++
→ 分散、易错、难版本控制
```

TSWoW 流程：
```typescript
// 一段 TS 代码，同时生成 DBC 记录 + SQL + 客户端补丁
const myItem = std.Items.create('mymod', 'epic-sword')
    .Name.enGB.set('传说之剑')
    .Quality.LEGENDARY.set()
    .Damage.addPhysical(500, 800)
```

编译一下，DBC、SQL、MPQ **全自动生成**。

### 优点

- **代码即内容**，可以 git 版本控制
- 类型安全，写错编译器就报错
- 自动处理 DBC <-> SQL 的 ID 对应关系
- 有完整的 API 文档
- 支持自定义类、法术、任务、地图

### 缺点（要认真考虑）

| 问题 | 说明 |
|---|---|
| **要用它的核心** | TSWoW 自带修改过的 TrinityCore，**不是模块** |
| **迁移成本高** | 你现有的 TrinityCore + NPCBot + Eluna 改造**没法直接搬过去** |
| 学习曲线 | 要学它的 API 体系 |
| 社区较小 | 遇到问题资料少 |

### 对你的评估

**不建议现在换。**

理由：
- 你已经在 `328950225/TrinityCore-NPCBOT-Eluna-zhCN` 上做了 28 个 step 的改造
- TSWoW 用自己的核心，NPCBot 和你的所有补丁都要重做
- **沉没成本太高**

**什么时候可以考虑**：
如果将来要**从零开一个新服**，且内容量很大（几百个自定义物品/法术），
TSWoW 的工程化优势才体现得出来。

## 二、数据库 GUI 编辑器 —— 别装 Keira3，装 WoWDatabaseEditor

### 【勘误 2026-07-31】我上一版推荐错了

初版我把 **Keira3 列为"建议加装"**，还写了句
"Keira3 是为 AzerothCore 做的，但 TrinityCore 的表结构基本兼容"。

**用户指出：Keira3 是 AzerothCore 专属的。用户是对的。**

查证：

| 项目 | 官方定位原话 |
|---|---|
| Keira2 | "Database Editor for the **TrinityCore** MMORPG framework" —— **2019-06-16 已归档停更** |
| Keira3 | "Official Database Editor for **AzerothCore**" |

Keira 的历史是：**Keira2 服务 TrinityCore → 归档 → 开发迁到 AzerothCore 做 Keira3**。
也就是说，**TrinityCore 支持是被主动放弃的那条路**。

社区还有人开了 `Krigsgaldrnet/Keira3-TC` 想改回支持 TrinityCore，
但仓库自述写着 "This code **will be** rewritten to support Trinitycore" ——
**还没做完**，而且警告 "So do not try on Azerothcore. It may not work!"。

**结论：Keira3 对你（TrinityCore 3.3.5 + 大量自定义表）不合适，别装。**

### 正确选择：WoWDatabaseEditor (WDE)

> 项目：https://github.com/BAndysc/WoWDatabaseEditor
> 561 star / 2020 commits / 最近提交 2026-03（5 个月内）
> 赞助方：Stormforge；参与方：**Atlantiss、Tauri**（都是大型 TC 系服务器）

**官方支持矩阵（README 原文）**：

```
Supported database: TC 3.3.5, TC 4.3.4, TC master (10.0.x), AzerothCore (3.3.5)
Supported DBC:      3.3.5, 4.3.4, 10.x
```

**第一个就是 TC 3.3.5 —— 正是你的版本。**

| 项 | 说明 |
|---|---|
| 运行环境 | .NET 8 Runtime（Win / Linux / Mac 都有）|
| 更新方式 | **内置自动更新器**，不用反复下 zip |
| 前身 | Visual SAI Studio（同作者，从零重写）|
| 特色 | **OpenGL 3D 视图**（能在 3D 里看/摆坐标）|
| DBC | 直接读 3.3.5 DBC |

Reddit 上 r/wowservers 的直接对比（2022）：

> "Wowdbeditor is MUCH better than Keira for smart scripts"
> "Very easy to handle, no knowledge needed, only logic.
>  Works for Azerothcore, and **Trinitycore based servers**."

**下载**（Windows 直链，AppVeyor 出的最新构建）：

### 它能编辑什么

一个图形界面，专门编辑 `world` 库的各种表：

| 编辑器 | 对应表 |
|---|---|
| Creature Editor | `creature_template` + 关联表 |
| Item Editor | `item_template` |
| Quest Editor | `quest_template` + `quest_template_addon` |
| GameObject Editor | `gameobject_template` |
| Loot Editor | 各种 `*_loot_template` |
| SmartAI Editor | `smart_scripts` |
| Gossip Editor | `gossip_menu` + `gossip_menu_option` |

### 对比 DBeaver（你在用的）

| | WoWDatabaseEditor | DBeaver |
|---|---|---|
| 定位 | **WoW 专用 IDE** | 通用数据库客户端 |
| TC 3.3.5 | **官方第一顺位支持** | 无概念 |
| 字段说明 | **有**，每个字段带注释 | 无，自己查 |
| 关联表 | **自动关联**（改生物同时改 addon）| 手动 |
| 枚举值 | **下拉/勾选**（如 npcflag）| 手填数字 |
| SmartAI | **可视化编辑** | 手填一堆数字 |
| 3D 视图 | **有**（OpenGL，能看坐标）| 无 |
| DBC | **能直接读** | 无 |
| 通用查询 / 批量 SQL | 弱 | **强** |
| 你的自定义表 | 不认识 | **能用** |

### 对你的评估

**推荐装，和 DBeaver 并存。**

| 任务 | 用哪个 |
|---|---|
| 批量 SQL、跑你写的 41_scene_tables.sql | **DBeaver** |
| 你自造的 `custom_scene` 等表 | **DBeaver**（WDE 不认识）|
| 精细调一个 NPC / 物品 | **WDE** |
| 写 SmartAI 脚本 | **WDE**（可视化，省太多事）|
| 做任务链 | **WDE** |
| 在 3D 里核对剧情 NPC 坐标 | **WDE** |

**特别是 SmartAI 和 3D 视图这两点，跟你的剧情工具链直接相关**：

- SmartAI —— 给剧情 NPC 加行为（走到某点、说话、放技能）的标准方案。
  `event_type` / `action_type` 全是裸数字，手填很痛苦，WDE 有下拉和说明。
- 3D 视图 —— 你 `.scene` 存的是坐标快照，
  WDE 能在 3D 里直接看这些点摆得对不对。

> **前置**：装 .NET 8 Runtime。有内置自动更新器，装一次就够。

## 三、其他框架类工具

### Eluna（你已经在用）

Lua 脚本引擎。适合快速原型和轻量逻辑，不用重编译。

**你的项目里的定位**：
- 用户明确说过「Eluna 的改动接受不了」（指 NPCBot 相关）
- 但做**智能 NPC** 那条线时决定「走 Eluna 另一条路」

### AIO

Eluna 的插件通信框架，让服务端能推送**自定义 UI** 到客户端。

**潜在用途**：
- 做游戏内的图形化菜单（比现在的 gossip 菜单强得多）
- 你的 `.setup` / `.bar` 等指令可以做成面板
- **需要玩家装插件**，这是最大障碍

之前讨论 `.combo` 一键连招时提到过这个方案（方案 C）。
