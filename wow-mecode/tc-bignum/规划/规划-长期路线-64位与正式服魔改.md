# 长期路线：内存瓶颈 / 64位 / 正式服魔改

> 立项：2026-08-01
> 状态：**深度调研，未动工**
> 用户明确态度：「不怕麻烦一定要做到」「必须做到」
> 因此本文档不做"劝退"，而是**给出每条路的真实代价和可行切入点**

---

## 一、先纠正一个可能的误解：4GB 不是你的真瓶颈

### 实测事实

社区反馈中，装满 HD 模型包的 3.3.5 客户端，
主要崩溃点是**达拉然人多时** —— 报 `ERROR #132` 或 "not enough memory"。

解法社区已验证有效：

| 方案 | 效果 |
|---|---|
| **LAA / 4GB Patch** | 2GB -> 4GB，**绝大多数情况够用** |
| **DXVK**（D3D9 转 Vulkan）| **显著降低显存和主存压力**，很多人靠这个彻底解决 |
| `SET gxTextureCacheSize` | 限制贴图缓存 |
| 关掉部分 HD 包 | 治标 |

**DXVK 这条特别值得试** —— 它把 D3D9 调用转成 Vulkan，
内存管理效率高一个档次。做法就是把 `d3d9.dll` 丢进客户端根目录。

### 关键判断

**4GB 用户空间 + DXVK，对 3.3.5 内容量来说很难撑爆。**

真要撑爆，通常是**贴图分辨率过高**（比如全套 4K 材质），
而不是"内容太多"。加一百个自定义物品、几十个种族模型，
根本吃不到 4GB。

**建议**：先装 DXVK 实测，确认瓶颈真的存在再谈 64 位。
**不要为一个还没发生的问题做最昂贵的方案。**

## 二、3.3.5 客户端 64 位化 —— 事实核查

### 结论：这不是"改造"，是"重写"

`Wow.exe 3.3.5.12340` 是 **32 位 PE 可执行文件**。
把它变成 64 位需要：

| 步骤 | 说明 | 可行性 |
|---|---|---|
| 反编译全部机器码 | 约 10MB x86 汇编 | 理论可行，产物无法维护 |
| 重写为 x64 | 指针宽度、调用约定、结构体布局全变 | **等于重写引擎** |
| 修复所有内联汇编和硬编码偏移 | 客户端大量依赖 | 极难 |
| 保证协议兼容 | 否则连不上服务端 | 难 |

**暴雪官方原话**（2011 蓝贴，社区存档）：

> At this time there are no plans to create a 64 bit executable as this would need
> to be tested along side of a 32 bit executable, effectively doubling the testing...

**连暴雪自己在有源码的情况下都觉得不划算。**
没有源码做这件事，工作量是重写一个引擎。

### 但有个替代方案能拿到 80% 的收益

**目标其实是"突破内存/性能限制"，不是"位数"本身。**

| 想要的 | 64位能给 | 有没有别的路 |
|---|---|---|
| 更多内存 | 是 | **DXVK + LAA 基本够** |
| 更好性能 | 有限 | **DXVK 提升更大** |
| 突破字段上限 | **给不了** | 见下 |

**注意最后一行** —— 你之前撞的 21.47 亿血量墙，
根因是 `UpdateFields.h` 里字段声明为 `Type: INT`（32位有符号），
这是**网络协议的字段宽度**，跟 exe 是 32 位还是 64 位**完全无关**。
改成 64 位 exe，那堵墙原封不动。

**真要突破那堵墙，得改协议字段布局** —— 那是另一个话题，
而且客户端和服务端要同步改，难度不亚于 64 位化。

## 三、正式服客户端魔改 —— 到底能改到什么程度

这是本文档最有价值的部分，因为**答案比想象的乐观，但有硬边界**。

### 3.1 服务端：完全可控

用 **CypherCore**（GPL-3.0，C#，支持 11.2.5）或 TrinityCore master。
**源码完整，想改什么改什么。** 这一半没有任何限制。

### 3.2 客户端：能改，但机制完全不同

| | 3.3.5 (MPQ) | 正式服 (CASC) |
|---|---|---|
| 数据格式 | MPQ 归档 | **CASC 内容寻址存储** |
| 文件标识 | **路径字符串** | **FileDataID（纯数字）** |
| 加自定义文件 | 丢个 `patch-Y.MPQ` | 需要 **Arctium 文件映射** 或 **CASCHost** |
| 工具成熟度 | 十几年积累 | 少且易失效 |

### 3.3 两条已验证的技术路线

**路线 A：Arctium Launcher 的自定义文件加载**

```
mappings/   放 fileId;filePath 映射表
files/      放你的自定义文件（按目录结构）
```

**优点**：轻量，不用自建 CDN
**缺点**：需要知道目标文件的 FileDataID，靠社区 listfile 查

**路线 B：CASCHost（`WowDevTools/CASCHost`）**

这是个**模拟暴雪 CDN 的 Web 服务**，官方描述：

> a specially designed web service that both builds and hosts modified a CAS container.
> This web service is designed to replicate Blizzard's own CDN meaning
> **a client works as seamlessly with custom content as with retail**.

**这就是你说的「替代暴雪官方服务器」的现成实现。**

配置项里有个关键设计：

> `MinimumFileDataId`: This is the smallest fileDataId for new files;
> this acts as **a buffer between official Blizzard files and custom ones to avoid collision**

也就是说 —— **自定义内容有专门的 ID 段，不会和官方文件冲突。**

**优点**：客户端完全无感，和玩官服一样
**缺点**：要 MySQL + 公网域名，架设复杂度高

### 3.4 【硬边界】8.2 之后文件名被移除

这是必须知道的一条限制。MMO-Champion 上的实测记录：

> As of 8.2 the client no longer uses file names, just FileDataIDs.
> ...Coming in 8.2 they are getting rid of 99% of the filenames.

**影响**：
- 8.2 之前：可以按路径覆盖文件（像 MPQ 那样）
- **8.2 之后：只能按 FileDataID 覆盖**，路径覆盖失效

**这意味着**：改一个贴图，你得先查出它的 FileDataID 是多少。
社区维护的 listfile 能查大部分，但**新文件和未命名文件查不到**。

### 3.5 现实评估

| 想做的 | 正式服可行性 |
|---|---|
| 改服务端逻辑/数值/指令 | **完全可以**（CypherCore 源码在手）|
| 加自定义物品/法术 | 可以（DB2 + CASCHost）|
| 替换模型/贴图 | 可以，但要查 FileDataID |
| **加全新种族/职业** | **难** —— 客户端 Lua/XML 被大量加密和校验 |
| 改 Interface | 比 3.3.5 难得多 |
| 跟随官方更新 | **每次大版本协议变，要重新适配** |

**最后一条是最大的现实成本**：暴雪每次更新，
CypherCore 社区要花数周到数月适配。你跟着更新 = 永远在追赶。

## 四、把正式服内容移植到 3.3.5 —— 反向思路

你说「想把正式版的种族和职业全部移植过来」。

**这条路比"魔改正式服"现实得多**，而且和你现在的工作是**加法**不是**推倒重来**。

### 4.1 已确认可行的部分

| 内容 | 可行性 | 依据 |
|---|---|---|
| **模型/贴图** | **可行** | wow.export 提取 + Multi Converter 转 MD20 |
| **音效音乐** | **可行** | 格式通用 |
| **图标** | **可行** | BLP 格式没变 |
| **12-21 预留种族** | **可行且免费** | 见 `规划-高版本种族移植.md` |
| 装备物品外观 | 可行 | 走 ItemDisplayInfo.dbc |

### 4.2 难的部分

| 内容 | 难点 |
|---|---|
| **新种族（熊猫人等）** | 突破 21 号上限要改 exe；骨骼/动画要转 |
| **新职业（DH/DK之外）** | 技能系统要从零写，客户端 Lua 要加职业 |
| **军团神器系统** | 纯服务端能仿，但 UI 要 AIO 插件 |
| **各版本特色系统** | 逐个评估，多数能用现有机制仿 |

### 4.3 关键洞察

**"特色系统"大部分可以用现有机制仿出来，不需要客户端支持。**

举例：

| 系统 | 3.3.5 实现思路 |
|---|---|
| 神器武器 | 自定义物品 + 法术 + gossip 升级界面 |
| 天赋树扩展 | 自定义法术 + `.talent` 类指令 |
| 属性强化 | 你已经做过的数值系统 |
| 幻化 | 已有（step16）|
| 坐骑收藏 | gossip 菜单 |

**只有"需要新的客户端 UI 框架"的系统才真的做不了。**
而那类系统可以用 **AIO**（Eluna 插件通信）推自定义 UI 到客户端 —— 
代价是玩家要装插件。

## 五、三条路的成本对比

| | A. 留 3.3.5 深耕 | B. 3.3.5 + 64位化 | C. 转正式服 |
|---|---|---|---|
| 已有成果 | **全保留** | 全保留 | **全废** |
| 内存瓶颈 | DXVK+LAA 解决 | 理论解决 | 天然无 |
| 客户端魔改 | **成熟（MPQ）** | 成熟 | **难（CASC+FileDataID）** |
| 加种族 | 12-21 免费，更多要改exe | 同左 | 几乎不可能 |
| 内容完整度 | **高** | 高 | 高（官方内容）|
| 工作量 | 持续积累 | **等于重写引擎** | 从零开始 |
| 跟随更新 | 不需要 | 不需要 | **永远在追** |

## 六、我的建议（分阶段，都能做，只是顺序）

### 阶段 1：先证伪内存瓶颈（1 小时）

```
1. 装 DXVK（d3d9.dll 丢进客户端根目录）
2. 确认 LAA 已打（你的补丁 exe 大概率有）
3. 装满你想要的 HD 包，去达拉然/奥格瑞玛人多的地方
4. 看会不会崩
```

**如果不崩 —— 64 位这条线可以直接封存，省下无限工时。**

### 阶段 2：继续 3.3.5 深耕（当前主线）

剧情工具链 -> 外观控制 -> NPCBot 增强 -> 客户端素材移植

**这条线每一步都有确定产出。**

### 阶段 3：正式服作为【第二战线】而非替代

```
用 CypherCore 搭一个测试环境
目标不是"取代 3.3.5"，而是"探路"
先做一件最小的事：加一个自定义 NPC 并改它的模型
记录：花了多久，卡在哪
```

**这个实验的价值**：用真实数据判断值不值得投入，
而不是靠猜。

### 阶段 4：64 位化 —— 只在阶段 1 证明确实需要时

即便到那一步，**也建议先找现成方案**：
- 社区有没有人做过（目前查证：没有成功案例）
- 有没有部分优化的 exe 补丁（有，比如 LAA、DXVK 兼容补丁）
