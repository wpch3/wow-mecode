# 突破人数上限 —— 三道墙的实证与拆法

> 2026-08-04
> 用户要求：「服务器总机器人上限可以上千上万，配置好甚至上十万，
> npcbot和playerbot都要这样。自己的bot也是同理。
> 队伍组队不止四十人，可以八十人一百人甚至上千人。
> 副本团本也要没有人数限制。」
>
> **别管什么限制，我们要的就是突破限制。**

---

## 零、先给结论表

| # | 目标 | 服务端能不能破 | 客户端能不能显示 | 难度 |
|---|---|---|---|---|
| 1 | 服务器 bot 总数上万 | **能** | 不涉及界面 | 低（配置+SQL） |
| 2 | 自己带的 bot 上限 | **能**（要改 uint8） | 超40不进团队框 | 中 |
| 3 | 队伍人数 > 40 | **能** | **这是真墙** | 高 |
| 4 | 副本人数无限制 | **能**（一处判定） | 不涉及界面 | 低 |

**先说最重要的一句**：第 3 条里「服务端能不能」和「客户端能不能显示」
**是两件事**，必须分开谈。下面每一条都给了行号。

---

## 一、服务器 bot 总数上万 —— 能，且不用改代码

### 1.1 真正的限制不是"数量上限"，是"模板池"

```cpp
// botdatamgr.cpp:1878
uint32 maxbots = sBotGen->GetSpareBotsCount();
uint32 enabledbots = sBotGen->GetEnabledBotsCount();

if (maxbots < wandering_bots_desired)
{
    BOT_LOG_FATAL("server.loading", "Only {} out of {} bots of enabled classes
        aren't spawned. Desired amount of wandering bots ({}) cannot be created. Aborting!");
    ASSERT(false);          // <- 【直接崩服】
}
```

`GetSpareBotsCount()` 数的是 `_spareBotIdsPerClassMap`（botdatamgr.cpp:62），
这个池子来自数据库表 `creature_template_npcbot_extras`：

```cpp
// botdatamgr.cpp:325
_spareBotIdsPerClassMap.at(c).insert(id);
```

**每生成一个游荡 bot 就消耗一个模板 ID**（botdatamgr.cpp:368 `erase(orig_entry)`）。

所以：

```
服务器 bot 总数上限  ==  数据库里有多少个 bot 模板
```

配置里写 10000，但库里只有 500 个模板 -> **启动直接 ASSERT 崩服**。

### 1.2 好消息：entry 空间已经放开了

```cpp
// botcommon.h:39-41
BOT_ENTRY_BEGIN          = 70001,
//BOT_ENTRY_END          = 71000,        <- 【被注释掉了】
BOT_ENTRY_CREATE_BEGIN   = 70800,        // 70800+ reserved for bot creation
```

上限那行**已经被上游注释掉**，说明作者自己就放开了。
`next_bot_id` 是 `uint32`（botdatamgr.cpp:291），理论能到 42 亿。

### 1.3 怎么做

**纯 SQL + 配置，不用编译**：

1. 批量往 `creature_template` + `creature_template_npcbot_extras`
   插入 N 个 bot 模板（用 SQL 循环生成，我可以出脚本）
2. `NpcBot.WanderingBots.Continents.Count = 10000`

**要注意的现实成本**（这个必须说清楚）：

| bot 数量 | 内存估算 | 每 tick CPU |
|---|---|---|
| 1,000 | 约 0.5-1 GB | 可接受 |
| 10,000 | 约 5-10 GB | 单核会吃紧 |
| 100,000 | 约 50-100 GB | **单进程扛不住** |

TrinityCore 是**单线程主循环**（`World::Update`），
每个 bot 每 tick 都要跑 AI。10 万个 bot 不是内存问题，是**主循环会卡死**。

**我的建议**：先做到 1000-5000 验证稳定性，再往上推。
不是"做不到"，是要**分批验证**，不然崩了不知道崩在哪。

## 二、自己带的 bot 上限 —— 能破，要改一个 uint8

### 2.1 墙的位置（三处，都是类型）

```cpp
// botconfig.h:30
using LvlBrackets = BotBrackets<uint8>;      // <- 存储类型 uint8

// botconfig.cpp:180
static LvlBrackets _max_npcbots;             // <- 最大只能存 255

// botconfig.h:121
static uint8 GetMaxNpcBots(uint8 level);     // <- 返回值 uint8
```

```cpp
// botconfig.cpp:485-488   还有个硬夹逼
if (uval >= MAX_RAID_SIZE)                   // MAX_RAID_SIZE = 40
{
    BOT_LOG_ERROR(...);
    uval = uint8(MAX_RAID_SIZE - 1);         // <- 强制压回 39
}
```

### 2.2 拆法

**要 40-255 个**：只删 `botconfig.cpp:485-489` 那个夹逼即可，
`uint8` 够用，改动最小。

**要 255 以上**：把三处 `uint8` 换成 `uint32`：

```cpp
// botconfig.h:30
using LvlBrackets = BotBrackets<uint32>;     // uint8 -> uint32

// botconfig.h:121
static uint32 GetMaxNpcBots(uint8 level);    // 返回值 uint8 -> uint32

// botconfig.cpp:1172  同步改实现签名
```

再删掉那个 `MAX_RAID_SIZE` 夹逼。

### 2.3 但是——超过 40 个之后，团队框显示不了

这是**客户端限制**，见第三章。bot 会正常存在、正常战斗，
但**第 41 个之后不会出现在你的团队框里**。

**这不是"做不到"，是"要额外做一层"**，第三章给方案。

## 三、队伍 > 40 人 —— 服务端能破，客户端是真墙

### 3.1 服务端：只有一处判定

```cpp
// Group.cpp:2779
return isRaidGroup() ? (m_memberSlots.size() >= MAX_RAID_SIZE)
                     : (m_memberSlots.size() >= MAX_GROUP_SIZE);
```

```cpp
// Group.h:43-45
#define MAX_GROUP_SIZE      5
#define MAX_RAID_SIZE       40
#define MAX_RAID_SUBGROUPS  MAX_RAID_SIZE / MAX_GROUP_SIZE     // = 8
```

**全仓库只有 36 处引用**（MAX_RAID_SIZE 6 处 / MAX_GROUP_SIZE 20 处 /
MAX_RAID_SUBGROUPS 10 处），改起来不算大。

把 `MAX_RAID_SIZE` 改成 1000，服务端就能让 1000 人进同一个 Group。
`m_memberSlots` 是 `std::list`，没有容量限制。

### 3.2 发包也支持 —— 这是好消息

```cpp
// Group.cpp:2034
data << uint32(GetMembersCount()-1);         // <- uint32，不是 uint8
```

**成员数用 uint32 发**，服务端发 1000 人的列表没问题。

### 3.3 真墙：客户端

#### 墙 1：子组 ID 是 uint8

```cpp
// Group.cpp:2053
data << uint8(citr->group);                  // groupid
```

`uint8` 最大 255 个子组，每组 5 人 -> **理论 1275 人**。
这条其实不算太死。

#### 墙 2：3.3.5 客户端团队框写死 8 组 x 5 人

这是**客户端 exe 里的硬编码**，不是服务端能改的：

```
团队框（RaidFrame）    最多 8 个子组，每组 5 格
CompactRaidFrame       同样按 40 人布局
```

**后果**：第 41 个成员开始，客户端团队框**不显示**。
但服务端认为他在队里 —— 他能收到队伍聊天、能共享拾取、
能被治疗（只要你手动选中他）。

#### 墙 3：某些包的成员遍历有隐式假设

需要逐个排查（战场记分板、副本锁定、LFG 等）。

### 3.4 三条可行路线（按代价排序）

#### 路线 A：服务端放开，接受客户端只显示 40 人（推荐先做）

```
改动：MAX_RAID_SIZE 40 -> 1000（Group.h:44）
     MAX_RAID_SUBGROUPS 相应变成 200
     m_subGroupsCounts 数组自动跟着变大（Group.cpp:3044 用的就是这个宏）

效果：1000 人真的在一个队里，能聊天、能共享经验/拾取
     客户端团队框只显示前 40 个
代价：低。工作量 1-2 轮
```

**这条最实际** —— 你要的"上千人组队"在**服务端语义上完全成立**，
只是界面看不全。对 bot 来说界面本来就不重要。

#### 路线 B：A + 自定义界面插件

```
额外做：一个 AddOn，用自定义框体显示全部成员
       （AddOn 能拿到 SMSG_GROUP_LIST 的全部数据）
效果：真的能"看见"1000 人
代价：中。要写 Lua AddOn，玩家都得装
```

#### 路线 C：改客户端 exe

```
效果：原生团队框支持更多人
代价：极高。要逆向 3.3.5 客户端、打二进制补丁、
     每个玩家都要用改过的 exe
```

**我的建议**：先做 A（服务端真突破），需要"看得见"时再上 B。
C 不是不能做，但收益/代价比太差，除非你明确要。

## 四、副本/团本人数无限制 —— 最容易的一条

### 4.1 墙只有一处

```cpp
// Map.cpp:3961-3967   InstanceMap::CannotEnter
uint32 maxPlayers = GetMaxPlayers();
if (GetPlayersCountExceptGMs() >= maxPlayers)
{
    TC_LOG_WARN("maps", "MAP: Instance '{}' of map '{}' cannot have more than
                '{}' players. Player '{}' rejected");
    return CANNOT_ENTER_MAX_PLAYERS;         // <- 就这一处
}
```

### 4.2 上限来自 DBC，可以用 SQL 覆盖

```cpp
// Map.cpp:4408
uint32 InstanceMap::GetMaxPlayers() const
{
    MapDifficulty const* mapDiff = GetMapDifficulty();
    if (mapDiff && mapDiff->maxPlayers)
        return mapDiff->maxPlayers;          // <- 优先用这个
    return GetEntry()->MaxPlayers;
}
```

`MapDifficulty` 来自 `MapDifficulty.dbc`，
但 TrinityCore 支持用 SQL 表覆盖 DBC 值。

### 4.3 两种做法

**做法 1（推荐）：SQL 改 maxPlayers，不用编译**

改 `MapDifficulty` 对应的 SQL 覆盖表，把 maxPlayers 设成 1000。

**做法 2：代码里直接跳过判定**

```cpp
// Map.cpp:3963  加一个 conf 开关
if (!sWorld->getBoolConfig(CONFIG_INSTANCE_IGNORE_PLAYER_LIMIT))
    if (GetPlayersCountExceptGMs() >= maxPlayers)
        return CANNOT_ENTER_MAX_PLAYERS;
```

**做法 2 更彻底**（所有副本一刀切），做法 1 更可控（按副本调）。
建议**两个都做**：conf 总开关 + SQL 精调。

## 五、PlayerBot 数量上限

### 5.1 PlayerBot 没有独立的数量限制

step40 的 `.pbot` 是我们自己写的，`g_pbots` 是 `std::vector`，没上限。

**真正的限制在别处**：

```cpp
// World.h:619-620
void SetPlayerAmountLimit(uint32 limit) { m_playerLimit = limit; }
uint32 GetPlayerAmountLimit() const { return m_playerLimit; }
```

对应 conf 的 `PlayerLimit`。**每个 PlayerBot 都算一个在线玩家**。

### 5.2 现实成本比 NPCBot 高得多

| | NPCBot | PlayerBot |
|---|---|---|
| 本体 | Creature | **完整 Player 对象** |
| 内存/个 | 约 50-100 KB | **约 500KB - 1MB** |
| 背包/任务/天赋 | 无 | **全套** |
| 存盘 | 轻 | **每个都要写 characters 库** |

**1000 个 PlayerBot 约等于 1000 个真人同时在线。**

这不是劝退，是要你知道**该在哪台机器上跑**。

### 5.3 结论

```
PlayerBot 数量        建议做法
--------------------------------------------------
10-50                 现在就能跑
100-500               要加 conf 调优 + 分批上线
1000+                 需要先做"分片/休眠"机制
                      （远离玩家的bot降低AI频率甚至不更新）
```

**"休眠机制"是关键**：让远处的 bot 每 10 秒才 update 一次，
而不是每 50ms。这样 10000 个 bot 的开销能压到 1000 个的水平。

这个机制**必须做**，否则数量上不去。我建议单独立一个 step。

## 六、执行顺序建议

```
第1阶段（低风险，立刻能做）
  1. 副本人数放开        Map.cpp 一处 + conf 开关
  2. 自己bot上限 40->255  删 botconfig.cpp:485 的夹逼
  3. bot模板批量生成SQL   解决"总数"的真正瓶颈

第2阶段（服务端真突破）
  4. MAX_RAID_SIZE 40 -> 1000
     配套改 MAX_RAID_SUBGROUPS、检查36处引用
  5. GetMaxNpcBots uint8 -> uint32

第3阶段（让数量真的能跑起来）
  6. bot 休眠/分片机制    <- 没有这个，数量堆不上去
  7. 分批上线，压测每一档

第4阶段（可选，看得见）
  8. 自定义团队框 AddOn
```

**每一阶段都要实测通过再进下一阶段** —— 这是你定的规矩，也是对的。
一次性全改，崩了不知道崩在哪。

## 七、我不会说"做不到"，但要说清代价

按最高铁律，逐条回答：

### 「上千人组队」

- **服务端**：能做，`MAX_RAID_SIZE` 一个宏 + 36 处引用检查
- **客户端团队框**：3.3.5 的 exe 写死 8x5，**这一条服务端改不了**
- **绕过方式**：自定义 AddOn 界面（路线 B），或接受"服务端成立但只显示40"

**所以准确的表述是**：
「上千人在同一个 Group 里」—— **能做到**
「原生团队框显示上千人」—— **要么改客户端，要么写 AddOn**

### 「10 万 bot」

- **entry 空间**：够（上游已注释掉 BOT_ENTRY_END）
- **数据结构**：够（std::map / std::list，无硬上限）
- **真瓶颈**：单线程主循环 + 内存

**所以准确的表述是**：
「10 万 bot 在数据结构上成立」—— **能做到**
「10 万 bot 同时跑 AI 不卡」—— **需要先做休眠/分片机制**

### 「副本无限人数」

- **能做**，一处判定 + DBC/SQL 覆盖，这条最干净
