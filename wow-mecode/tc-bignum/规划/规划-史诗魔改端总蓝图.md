## 二、⚠️ 必须先知道的 5 个硬边界

我把源码全部核对了一遍，这些是**物理限制**，不是"努力一下就能突破"的。
在动工前理解它们，能省掉大量白工。

### 边界 1：等级上限 —— 255 是可以的，但 100 以上要补 DBC

源码里三个常量（`src/server/shared/DataStores/DBCEnums.h:40-54`）：

```cpp
enum LevelLimit : uint8
{
    DEFAULT_MAX_LEVEL = 80,   // 默认值
    MAX_LEVEL         = 100,  // 客户端安全上限
    STRONG_MAX_LEVEL  = 255,  // 服务端理论上限
};
```

- **等级字段本身没问题**：`UNIT_FIELD_LEVEL` 是 `INT`（32位），
  但 `GetLevel()` 返回 `uint8`，所以 **255 是真正的天花板**，再高要改一大片代码
- **`MAX_LEVEL = 100` 是配置校验上限**（`World.cpp:897`），改成 255 即可
- **真正的坑在 GT 表**：`GT_MAX_LEVEL = 100`（`DBCStructure.h:758`）
  这是 `gtOCTRegenHP/MP`、`gtRegenHPPerSpt`、`gtChanceToMeleeCrit` 等
  **等级缩放 DBC 的行数**。超过 100 级后，法力回复、暴击率、闪避率等
  全部取不到值 → 归零或读越界

**要做的事**：
1. 改三个常量
2. **重新生成所有 gt*.dbc**，把行数从 100 扩到 255
3. 补 `player_classlevelstats`（每职业每级基础血蓝）
4. 补 `player_levelstats`（每种族每职业每级五维）
5. 补 `player_xp_for_level`（升级所需经验，源码已支持到 `STRONG_MAX_LEVEL`）

> 数据量：11 职业 × 255 级 = 2805 行，10 种族 × 11 职业 × 255 级 = 28050 行。
> **必须写脚本生成，手填不现实。**

### 边界 2 & 3（已更正）：新种族/新职业 —— **可以加，且能加多个**

> ⚠️ **我最初的说法是错的，已更正。**
> 原先写"需要逆向客户端 exe""只能加 1 个职业"，都不准确。

**真相**：3.3.5 客户端的种族/职业列表**不在 exe 硬编码里**，而是读取：

| 位置 | 内容 |
|---|---|
| `ChrRaces.dbc` / `ChrClasses.dbc` | 种族/职业定义 |
| `CharBaseInfo.dbc` | 哪个种族能选哪个职业 |
| `Interface\GlueXML\CharacterCreate.lua` | **`MAX_RACES` / `MAX_CLASSES_PER_RACE` 上限在这里** |
| `Interface\GlueXML\CharacterCreate.xml` | 创建界面的按钮布局 |

这些全部可以打包进 MPQ 补丁，**不需要动 exe**。
社区有完整的加职业记录（stoneharry/WoW-Custom-Class）和加种族教程，
也有现成的 "All Races All Classes" 模块。

职业同样可以往 11 号之后继续加：
```cpp
CLASS_DRUID = 11,
CLASS_MONK  = 12,     // 社区实测可行
#define MAX_CLASSES 13
```
源码注释里种族 12~21（娜迦、维库人、食人魔等）都是暴雪预留 ID。

#### 但真正的成本在这里（比"逆向"更实际的坑）

**① 服务端有一堆 `MAX_CLASSES` 定长数组，改大后必须逐个补数值**

我实测搜出这些（改大 MAX_CLASSES 后初始化列表元素不够，编译报错或运行越界）：

```cpp
ObjectMgr.h:1670       _playerInfo[MAX_RACES][MAX_CLASSES]
StatSystem.cpp:690     m_diminishing_k[MAX_CLASSES]
StatSystem.cpp:728     miss_cap[MAX_CLASSES]
StatSystem.cpp:754     parry_cap[MAX_CLASSES]
StatSystem.cpp:796     dodge_cap[MAX_CLASSES]
Player.cpp:5249        dodge_base[MAX_CLASSES]
Player.cpp:5264        crit_to_dodge[MAX_CLASSES]
CommonHelpers.cpp:189  PlayerSpecializationIconicSpells[MAX_CLASSES][...]
spell_item.cpp:318     triggeredSpells[MAX_CLASSES]
```

**② 客户端会崩溃的三个已知点**

| 症状 | 原因 |
|---|---|
| 打开天赋/角色面板**直接崩客户端** | 缺 `gt*.dbc` 对应新职业的数据 |
| who 列表报错 | `Interface\FrameXML\Constants.lua` 的 `RAID_CLASS_COLORS` 没加 |
| **角色不会说话、不能穿装备** | `SkillLineAbility.dbc` + `SkillRaceClassInfo.dbc` 没配 |

**③ 每加一个种族/职业的固定工作量**

```
改 5~8 个 DBC  +  改 GlueXML(lua/xml/blp)  +  补 C++ 定长数组
+ 填 playercreateinfo / player_levelstats / player_classlevelstats
+ 配 SkillLineAbility / SkillRaceClassInfo
```

**结论：十几个种族十几个职业完全能做到，私服就是这么来的。
难度不在"技术不可行"，而在"极其繁琐且线性叠加"。**

### 边界 4：新地图 —— 必须两端同步，且要做 MPQ 补丁

新地图需要：
1. **客户端**：用 Noggit 制作 ADT 地形 → 打包成 MPQ 补丁分发给玩家
2. **服务端**：从新 MPQ 提取 maps/vmaps/mmaps
3. **DBC**：`Map.dbc`、`AreaTable.dbc`、`WorldMapArea.dbc`、`WorldMapOverlay.dbc`
4. **每个玩家都要装补丁**，否则进图掉线

> 这是整个项目**工作量最大**的部分。一张完整地图 = 数百小时。

### 边界 5：客户端改造的分发问题

所有"客户端侧"改动（新模型、新地图、新界面、DBC）
最终都要打包成 **MPQ 补丁**（`Patch-4.MPQ` 之类）放进客户端 `Data` 目录。

**意味着**：
- 玩家必须下载你的定制客户端或补丁包
- 补丁体积可能 1~10 GB
- 每次更新都要重新分发

## 五、"真龙"种族的具体实现建议

这是你构想里最核心的部分，单独展开。

> 📌 **补充设定（用户后续明确）**：真龙「可控制使用所有生物和力量、
> 可召唤所有生物、可变成所有种族、可融合泰坦与噩梦之力」。
> 因此**自动战斗系统是设定的一部分，不是可选功能**。
> 详细技术方案见 `规划-游戏内难度菜单.md` 的**附录 C**。
>
> 关键发现：NPCBot 自带 **19 个职业 AI**，其中 9 个是魔兽3英雄单位
> （大法师/恐惧魔王/海巫/地穴领主等），正好可作为真龙不同形态的
> 战斗逻辑素材。

### 设定拆解

> 五色守护巨龙 + 所有星灵共同孕育，能承接**泰坦**与**噩梦**两种力量

### 技术方案（推荐）

| 层面 | 做法 |
|---|---|
| **种族槽位** | 占用现有种族（建议血精灵/德莱尼，模型骨骼较通用） |
| **阵营** | 改 `ChrRaces.dbc` FactionID 做成中立，或双阵营可选 |
| **外观** | `DisplayID` 换成巨龙模型（现成的有：奥妮克希亚、死亡之翼、五色龙） |
| **形态切换** | Lua 挂两个变身技能：泰坦形态（金色/机械感）、噩梦形态（暗紫/腐蚀） |
| **专属技能树** | 用 10 号职业槽位，或用 Lua 自定义技能菜单 |
| **属性成长** | `player_levelstats` 给这个种族配超高成长曲线 |
| **专属任务线** | 从出生地开始的独立主线 |

### 占用现有种族 vs 新增种族 —— 两条路都可行

| | 占用现有种族 | 新增种族(如 12~21 号) |
|---|---|---|
| 客户端补丁 | 小（只换 DisplayID） | 中（DBC + GlueXML + 模型） |
| 工作量 | 低 | 中高 |
| 代价 | 失去一个原种族 | 无，但要补全所有联动表 |
| 稳定性 | 高 | 需仔细测试崩溃点 |

**建议**：真龙作为"绝对主角"，值得走**新增种族**这条路。
但可以先用"占用现有种族"做原型验证玩法，跑通后再迁移到独立种族 ID。

## 六、等级 255 的完整改造清单

单独列出来，因为这是**第 1 阶段就能做**的高收益项目。

### 服务端改动

```cpp
// src/server/shared/DataStores/DBCEnums.h
DEFAULT_MAX_LEVEL = 255,   // 原 80
MAX_LEVEL         = 255,   // 原 100

// src/server/shared/DataStores/DBCStructure.h:758
#define GT_MAX_LEVEL 255   // 原 100  ★关键
```

### DBC 改动（必须，否则高等级属性全是 0）

需要把这些表的行数从 100 扩到 255：

```
gtOCTRegenHP.dbc          每级血量回复
gtOCTRegenMP.dbc          每级法力回复
gtRegenHPPerSpt.dbc       精神转血量回复
gtRegenMPPerSpt.dbc       精神转法力回复
gtChanceToMeleeCrit.dbc   近战暴击率
gtChanceToMeleeCritBase.dbc
gtChanceToSpellCrit.dbc   法术暴击率
gtChanceToSpellCritBase.dbc
gtCombatRatings.dbc       战斗等级换算 ★最重要
gtOCTClassCombatRatingScalar.dbc
gtNPCManaCostScaler.dbc
```

> `gtCombatRatings.dbc` 决定"多少 rating = 1% 暴击"，
> 不扩的话 100 级以上所有 rating 类属性全部失效。

### 数据库改动

| 表 | 行数 | 生成方式 |
|---|---|---|
| `player_classlevelstats` | 11职业 × 255级 = 2805 | 脚本生成 |
| `player_levelstats` | 10种族 × 11职业 × 255级 = 28050 | 脚本生成 |
| `player_xp_for_level` | 255 | 脚本生成 |

### 需要检查的连带影响

- **NPCBot 的等级分档**：`botcommon.h:29` 有
  `BRACKETS_COUNT = DEFAULT_MAX_LEVEL / 10 + 1`，改 255 后会自动扩展，但要测试
- **战场分级**：`BG_BRACKET_ID_LAST = 15`，可能需要调整
- **怪物等级**：`creature_template.maxlevel` 也要相应提升
- **物品需求等级**：`RequiredLevel` 是 tinyint(255)，刚好够用

建议按阶段验收，每完成一个阶段就能玩，而不是憋大招。

### 2. 优先做"零补丁"的内容

玩家最反感的就是下载几个 G 的补丁。
**阶段一到四全部不需要客户端补丁**，这部分做扎实，
你的服务器已经和普通端完全不同了。

### 3. 版本控制要跟上

改动会越来越大，务必：
- 每个阶段一个 git 分支
- DBC / MPQ 补丁也要版本化管理
- 数据库改动全部写成可重复执行的 SQL 脚本

### 4. 关于 NPCBot 的兼容

你这个整合包带 NPCBot。改等级上限、加种族职业时，
**NPCBot 的数据表也要同步**（`creature_template_npcbot_*`），
否则 bot 会卡在 80 级或读不到新职业。
