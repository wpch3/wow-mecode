## 一、第 1 阶段之后还有什么

### 已完成（第 1 阶段）

[x] unlimited.conf       本轮补上（之前只在说明里提到，没给文件）

### 第 2 阶段：服务端真突破（2-3 轮）

| # | 内容 | 改动量 | 风险 |
|---|---|---|---|
| 2.1 | `MAX_RAID_SIZE` 40 -> 1000 | 1个宏 + 检查36处引用 | 中 |
| 2.2 | `GetMaxNpcBots` uint8 -> uint32（突破255） | 3处类型 | 低 |
| 2.3 | `MAX_RAID_SUBGROUPS` 连带调整 | 自动跟随宏 | 低 |

**2.1 的关键约束**（已实查）：

```cpp
Group.cpp:2779   IsFull()  <- 全服【唯一】人数判定，改这里
Group.cpp:2034   data << uint32(GetMembersCount()-1);   <- 好消息：发包是uint32
Group.cpp:2053   data << uint8(citr->group);            <- 子组ID uint8，255组=1275人上限
Group.cpp:3044   m_subGroupsCounts = new uint8[MAX_RAID_SUBGROUPS];  <- 自动跟随
```

**做完的效果**：1000 人真的在同一个 Group 里，能聊天、共享拾取、共享经验。
**但客户端团队框只显示前 40 个**（3.3.5 exe 硬编码 8组x5）。

**什么时候做**：第 1 阶段实测稳定后，**随时可做**。
建议和 bot 数量测试一起做——你要带 250 个 bot，本来就需要队伍能装下。

### 第 3 阶段：休眠/分片机制（3-4 轮）【关键】

**这一阶段不做，数量就堆不上去。**

```
问题：TrinityCore 单线程主循环，每个 bot 每 tick 都跑完整 AI
     1000个 -> 可接受
    10000个 -> 单核吃紧
   100000个 -> 主循环卡死
```

**方案**：按距离分级更新频率

| bot 状态 | 更新频率 | 省下的开销 |
|---|---|---|
| 玩家视野内 / 战斗中 | 每 tick（原样） | 0% |
| 同地图但远离玩家 | 每 2 秒 | ~95% |
| 不同地图 / 无人区 | 每 30 秒或完全冻结 | ~99% |

**理论效果**：10000 个 bot 的开销压到接近 1000 个。

**技术入口**（初步查证，做的时候要再细查）：
```
bot_ai.cpp  UpdateAI(uint32 diff)     <- 加频率控制
Object.h    setActive(bool)            <- 非活跃对象降低更新
Map.cpp     Map::Update                <- 网格级别的批量控制
```

**什么时候做**：等你实际跑到 **1000+ bot 感觉卡** 的时候。
现在 500 个应该无感，没必要提前优化。

### 第 4 阶段：自定义团队框 AddOn（可选）

让客户端能"看见" 40 人以上。

```
服务端已经发了完整数据（Group.cpp:2034 是 uint32）
只是原生 UI 不显示 -> 写个 AddOn 用自定义框体渲染
```

**代价**：要写 Lua AddOn，每个玩家都得装。
**什么时候做**：只有当你确实需要"看见"上千人时才做。对 bot 来说界面不重要。

## 三、客户端魔改 vs 现有 patch 的兼容性

这个问题问得很关键。我按**风险等级**分类。

### 3.1 完全不受影响（绝大多数）

**纯服务端逻辑**，客户端改什么都不影响：

```
step34  伙伴关怀        服务端给物品 + 发聊天
step40  PlayerBot       服务端造 Player 对象
step42  自动接受        服务端调 handler
step43  Bot改名         改数据库
step44  招募闪退修复    服务端空指针
step46  副本人数        服务端判定
step48  游荡bot崩溃     服务端空指针
step49  永久化 .pin     数据库落库
step50  羁绊系统        服务端数据 + 聊天
```

**这些 patch 和客户端魔改是两条平行线，互不干扰。**

### 3.2 需要注意的（客户端改了会有影响）

| patch | 依赖客户端什么 | 客户端改了会怎样 |
|---|---|---|
| **step41/48 汉化** | `npc_text` 走服务端发文本 | **不受影响**（文本是服务端发的）|
| **step51 换外观** | `modelid1` 要在客户端 MPQ 里存在 | **换了模型包要重新挑ID** |
| **step31 .disguise** | 同上 | 同上 |
| **step32 .findmodel** | 读 DBC 里的模型表 | **换DBC要重新导出** |
| **数值改造（阶段一）** | 客户端 UpdateFields 是 INT32 | 已知天花板21.47亿，不变 |

**核心结论**：**只有"和模型/DBC 有关"的 patch 需要跟着客户端走。**

### 3.3 真正的风险：客户端补丁 vs 服务端 DBC 不一致

这是最容易出问题的地方，**不是 patch 兼容性问题，是数据一致性问题**：

```
客户端 MPQ 里有  模型ID 12345
服务端 DBC 里没有 12345
-> 服务端不认，creature_template 填了也不显示

反过来：
服务端 DBC 有    模型ID 12345
客户端 MPQ 没有
-> 客户端显示成"绿色问号"或直接崩客户端
```

**规则：客户端和服务端的 DBC 必须是同一套。**

你之前规划过装"全量模型包 9.2.5"（178,479文件/14.8GB），
那个装完**必须把配套 DBC 同步到服务端的 `dbc/` 目录**，否则会出上面的问题。

### 3.4 建议的做法

```
1. 客户端魔改【集中做完再统一测】，不要边改边加 patch
2. 每次换 DBC/模型包，重跑一次 .findmodel 确认能查到新模型
3. step51 换外观的 SQL，在换模型包【之后】再执行
   （因为模型ID会变）
4. 服务端 dbc/ 目录和客户端 Data/ 目录做个版本记录
```

**我的判断**：现有 patch **95% 以上完全不受客户端魔改影响**。
需要留意的只有模型ID 那几个，而且它们本来就是"数据配置"，
换了模型包重新配一遍就行，**不需要改代码**。

## 四、一个额外提醒

你现在同时在推进很多线：

```
bot数量上限 / 羁绊系统 / 换外观 / PlayerBot / 客户端魔改
```

**建议每次只让一条线处于"未验证"状态**。

比如现在：step46 刚跑通模板生成，就先把它验证完
（重启看到 "Set up spawning of 500 wandering bots"），
再装羁绊系统。这样出问题能立刻定位是哪一条线。

**同时装三个未验证的东西，出问题要花三倍时间排查。**
（这次的 `Duplicate entry` 就是因为 SQL 一次跑太多步才发现得晚）
