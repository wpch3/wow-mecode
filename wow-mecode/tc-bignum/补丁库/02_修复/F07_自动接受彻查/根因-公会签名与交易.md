# step53 自动接受彻查：公会签名灰色 + 交易面板不显示

> 用户反馈：「公会无法点击要求签名（灰色的无法点击），以及交易面板ui也没有显示」
> 「我只测试了这三个，就出现了两个问题」
>
> **两个问题性质完全不同**，下面分开说。

---

## 一、公会「签名」灰色 —— 我 step42 根本没做这个功能

### 1.1 你点的不是"公会邀请"，是"公会请愿书签名"

这是**两条完全独立的流程**：

| 流程 | 触发方式 | 服务端状态 | step42 覆盖了吗 |
|---|---|---|---|
| **公会邀请** | `.ginvite` / 公会面板邀请 | `SetGuildIdInvited(m_id)` | **做了** |
| **请愿书签名** | 右键请愿书 -> 点目标 | **不存状态** | **没做** |

### 1.2 为什么"不存状态"就做不了轮询

```cpp
// PetitionsHandler.cpp:513  HandleOfferPetitionOpcode
// 玩家把请愿书递给目标时：
Player* player = ObjectAccessor::FindConnectedPlayer(offererGuid);
...
// 一堆检查后，直接给目标【发包】，然后就结束了
```

```cpp
// PetitionsHandler.cpp:383  HandleSignPetition
// 目标点"签名"时才走这里
recvData >> petitionGuid;      // <- 需要请愿书的 GUID
```

**关键**：服务端**没有任何字段**记录"这个人正被要求签名"。
那个 GUID 只存在于**发给客户端的包里**。

bot 没有客户端 -> 包被丢弃（`WorldSession.cpp:211 if (!m_Socket) return;`）
-> **bot 永远不知道有人要它签名**。

> 这和 step42 调查过的「准备确认(Ready Check)」是**同一类问题**：
> 纯广播、服务端不留状态 -> 无法轮询。

### 1.3 为什么按钮是灰的

灰色不是 bug —— 客户端在等 bot 那边回 `SMSG_PETITION_SIGN_RESULTS`。
bot 永远不回，所以永远灰着。

### 1.4 能做，但要用【钩子】而不是轮询

`HandleOfferPetitionOpcode` 是 public（WorldSession.h），
我们可以在**它发包给 bot 之前**截住，直接让 bot 签名。

**这个我可以做，见第三章的方案。**

## 二、交易面板不显示 —— 我 step42b 的实现是错的

### 2.1 我用错了包

我的 `TryAcceptTrade` 调的是：

```cpp
bot->GetSession()->HandleBeginTradeOpcode(dummy);
```

它内部只做一件事：

```cpp
// TradeHandler.cpp  HandleBeginTradeOpcode
TradeStatusInfo info;
info.Status = TRADE_STATUS_OPEN_WINDOW;      // <- 只发这个
my_trade->GetTrader()->GetSession()->SendTradeStatus(info);
SendTradeStatus(info);
```

**但真正让客户端弹出交易框的是另一个包**：

```cpp
// TradeHandler.cpp:727  HandleInitiateTradeOpcode 的结尾
info.Status = TRADE_STATUS_BEGIN_TRADE;      // <- 【这个才弹窗】
info.TraderGuid = _player->GetGUID();        // <- 而且要带对方GUID
pOther->GetSession()->SendTradeStatus(info);
```

```cpp
// TradeHandler.cpp:43-50  两个状态发的数据都不一样
switch (info.Status)
{
    case TRADE_STATUS_BEGIN_TRADE:
        data << info.TraderGuid;      // 带GUID -> 客户端知道跟谁交易 -> 弹窗
        break;
    case TRADE_STATUS_OPEN_WINDOW:
        data << uint32(0);            // 只有个0 -> 客户端不知道弹什么
        break;
}
```

### 2.2 所以实际发生了什么

```
你发起交易
  -> HandleInitiateTradeOpcode 给【你】发 BEGIN_TRADE   （你这边本该弹窗）
  -> 双方 m_trade 都创建
  -> 我的轮询检测到 bot 有 m_trade
  -> 调 HandleBeginTradeOpcode -> 发 OPEN_WINDOW
  -> 这个包【覆盖】了你刚收到的状态，把窗口状态搞乱
```

**我不但没帮上忙，还可能把你本来能弹的窗口给弄没了。**

### 2.3 正确的做法：什么都不用做

再看一遍源码：

```cpp
// TradeHandler.cpp:723-729  玩家发起交易时
_player->m_trade = new TradeData(_player, pOther);
pOther->m_trade  = new TradeData(pOther, _player);

info.Status = TRADE_STATUS_BEGIN_TRADE;
info.TraderGuid = _player->GetGUID();
pOther->GetSession()->SendTradeStatus(info);    // 发给bot（被丢弃，无所谓）
```

**服务端这边交易【已经建立了】** —— 双方 `m_trade` 都有了。

bot 收不到那个包**根本不影响交易本身**，因为 bot 不需要"看见"窗口。
你这边的窗口是 `HandleInitiateTradeOpcode` 直接发给你的，
**和 bot 一点关系都没有**。

**所以 step42b 的 `TryAcceptTrade` 是多余的，而且有害。**

## 三、修复方案

### 3.1 交易【必做】：删掉这个功能

**最省事也最正确的做法：把 `PBOT_AUTO_TRADE` 整个去掉。**

打开 `pbot_autoaccept.cpp`，**Ctrl+F 搜**：

```cpp
    if (e.AutoFlags & PBOT_AUTO_TRADE)      TryAcceptTrade(bot);
```

**改成**（直接注释掉）：

```cpp
    // step53: 【已移除】TryAcceptTrade 是错的。
    //   我原本调 HandleBeginTradeOpcode 发 TRADE_STATUS_OPEN_WINDOW，
    //   但真正弹窗的是 TRADE_STATUS_BEGIN_TRADE（TradeHandler.cpp:727），
    //   而那个包在玩家发起交易时【已经由核心发给玩家了】。
    //   我这个多余的包反而会把玩家的窗口状态搞乱。
    //
    //   交易【本来就不需要bot配合】：TradeHandler.cpp:723-725
    //   双方 m_trade 在 HandleInitiateTradeOpcode 里就都建好了。
    //   bot 收不到包完全不影响交易本身。
    // if (e.AutoFlags & PBOT_AUTO_TRADE)      TryAcceptTrade(bot);
```

同样注释掉 `PBotForceAcceptAll` 里的那一行：

```cpp
    // TryAcceptTrade(bot);      // step53: 同上，已移除
```

**改完交易就正常了** —— 因为本来就不需要 bot 做任何事。

> `TryAcceptTrade` 函数本体可以留着（不调用就不会执行），
> 也可以一并删掉。留着的话编译器可能警告"未使用的函数"，
> 加个 `[[maybe_unused]]` 或直接删。

### 3.2 公会签名【新增】：用钩子实现

签名没法轮询，但可以在**核心发包给 bot 之前**截住。

需要改一处上游文件。

**Ctrl+F 搜**（`PetitionsHandler.cpp:513`）：

```cpp
void WorldSession::HandleOfferPetitionOpcode(WorldPacket& recvData)
{
    TC_LOG_DEBUG("network", "Received opcode CMSG_OFFER_PETITION");   // ok

    ObjectGuid petitionGuid, offererGuid;
    uint32 junk;
    recvData >> junk;                                      // this is not petition type!
    recvData >> petitionGuid;                              // petition guid
    recvData >> offererGuid;                               // player guid

    Player* player = ObjectAccessor::FindConnectedPlayer(offererGuid);
    if (!player)
        return;
```

**在 `if (!player) return;` 下面插入**：

```cpp
    //step53: PlayerBot 自动签名。
    //  请愿书签名是【纯发包】流程，服务端不存"待签名"状态
    //  （PetitionsHandler.cpp:383 HandleSignPetition 要从包里读 petitionGuid），
    //  所以无法用轮询实现，只能在这里截住。
    //
    //  bot 没有 socket，收不到 SMSG_PETITION_SIGN_RESULTS，
    //  客户端那边按钮就一直是灰的。
    //  这里直接替 bot 走一遍签名流程。
    if (player->GetSession() && player->GetSession()->PlayerDisconnected())
    {
        WorldPacket signPkt(CMSG_PETITION_SIGN, 8 + 1);
        signPkt << petitionGuid;
        signPkt << uint8(0);
        player->GetSession()->HandleSignPetition(signPkt);
        return;
    }
```

**依赖确认**（都实查过）：

```
WorldSession.h:503   PlayerDisconnected() { return !m_Socket; }   public
WorldSession.h       HandleSignPetition(WorldPacket&)             public(706段)
Opcodes.h            CMSG_PETITION_SIGN
PetitionsHandler.cpp:387-390  recvData >> petitionGuid; recvData >> unk;
                              <- 包格式：ObjectGuid + uint8，和上面构造的一致
```

> **为什么用 `PlayerDisconnected()` 而不是 `IsBotSession()`**：
> 前者是上游原生的（`WorldSession.h:503`），不依赖我们加的字段，更稳。

### 3.3 公会签名【替代方案】：不改上游

如果你不想动 `PetitionsHandler.cpp`，还有个办法：

**用 `.pbot accept` 手动触发** —— 但这需要知道 petitionGuid，
而那个 GUID 只在包里……**所以这条路走不通。**

**结论：要做签名，就必须改那一处上游。** 改动只有 10 行。

## 四、我这轮的失误

| 问题 | 我错在哪 |
|---|---|
| 交易 | **只看了函数名就用**。`HandleBeginTradeOpcode` 听起来像"开始交易"，实际只发 OPEN_WINDOW；真正弹窗的是 `HandleInitiateTradeOpcode` 结尾的 BEGIN_TRADE |
| 公会签名 | **把"公会邀请"和"请愿书签名"当成一回事**。我做了前者，你测的是后者 |

**共同点**：我没有**实际验证包的流向**，只看了状态字段就以为覆盖了。

**教训**：涉及"客户端 UI 有没有反应"的功能，
必须**追到具体发的是哪个 opcode、带什么数据**，
不能只看服务端状态字段。（这和之前"BuildValuesUpdate 过滤层"是同一类问题。）

已记入坑表。
