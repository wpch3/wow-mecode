# step62  `.pin` 的两个致命错误 —— 根因与重做

> 用户实测反馈：
> 1. 「用了fix后招募会闪退」
> 2. 「固定失败：SaveToDB 没能生成 spawnId」
> 3. 「重启后会找不到这个机器人，还是刷新了」

**两个都是我的错，而且是根本性的设计错误。下面逐条摊开。**

## 一、致命错误1：`.pin` 从来就没成功过

### 1.1 你看到的

```
固定失败：SaveToDB 没能生成 spawnId
已自动回滚，bot 保持游荡状态
```

这个回滚是我 step60 加的，**它正确地拦住了一次失败**。
但为什么会失败？

### 1.2 根因：上游有一道我没查到的门

`Creature.cpp:1427-1432`：

```cpp
void Creature::SaveToDB(uint32 mapid, uint8 spawnMask, uint32 phaseMask)
{
    //npcbot: disallow saving generated bots
    if (IsNPCBot() && GetBotAI() && (GetBotAI()->IsWanderer() || IsSummon()))
        return;                    // <-- 【第一行就 return】
    //end npcbot

    if (!m_spawnId)
        m_spawnId = sObjectMgr->GenerateCreatureSpawnId();
    ...
```

**只要 `IsWanderer()` 为真，`SaveToDB` 什么都不做直接返回。**

### 1.3 我 step49 的调用顺序是反的

看我写的代码（`cs_botpersist.cpp`）：

```
357行   BotDataMgr::AddNpcBotData(...)      <- 写 characters_npcbot   [成功]
```

**必须先 `UnsetWanderer()` 再 `SaveToDB()`。我顺序写反了。**

### 1.4 这解释了你之前遇到的一切

```
.pin 执行

  -> .pin 说"已经有持久化数据了"

```

**step60 我只治了"两个指令判断不一致"这个表象，

而不是只做个 `.pin fix` 去擦屁股。

## 二、致命错误2：`.pin fix` 会造成野指针崩服

### 2.1 你看到的

> 「用了fix后招募会闪退」

### 2.2 根因：`bot_ai` 构造时缓存了指针

`bot_ai.cpp:164`（构造函数初始化列表）：

```cpp
_botData(const_cast<NpcBotData*>(BotDataMgr::SelectNpcBotData(
    IsTempBot() ? creature->ToTempSummon()->GetSummonerGUID().GetEntry()
                : creature->GetEntry()))),
```

**每个 bot 在创建时就把 `NpcBotData*` 存进 `_botData` 成员变量。**

### 2.3 我的 `CleanupBroken` 把它 erase 了

`botdatamgr.cpp:3114-3123`：

```cpp
case NPCBOT_UPDATE_ERASE:
{
    NpcBotDataMap::iterator bitr = _botsData.find(entry);
    ASSERT(bitr != _botsData.end());
    _botsData.erase(bitr);              // <-- 【map 里的对象被销毁】
    ...
}
```

**`_botsData` 是 `std::unordered_map<uint32, NpcBotData>`（存值不存指针）。**

erase 之后，那个 `NpcBotData` 对象**被析构了**，
但 `bot_ai::_botData` 还指着那块已释放的内存 -> **野指针**。

### 2.4 一碰就崩

```bash
grep -c "_botData->" bot_ai.cpp
# 73
```

**73 处解引用，几乎没有判空**（只有 4 处判的是 `_botData->owner` 的值，
不是判 `_botData` 本身）。

招募流程会读 `_botData` -> **访问已释放内存 -> 闪退**。

### 2.5 所以 `.pin fix` 只能用在【bot 不在世界里】的时候

或者：**erase 之后必须让 bot 立刻从世界消失**，不给它被访问的机会。

## 三、致命错误3：修复后重启，bot 消失了

> 「重启后会找不到这个机器人，还是刷新了」

这个**其实是正常的**，但我没说清楚，导致你的预期错了。

### 3.1 游荡bot本来就是"每次重启重新生成"的

`botdatamgr.cpp:210`：

```cpp
if (!bot->LoadBotCreatureFromDB(0, map, true, true, bot_id, &spawnPos))
//                              ^ spawnId=0        ^ generated=true
```

`botdatamgr.cpp:460` 官方注释：

```cpp
//We do not create CreatureData for generated bots
```

**游荡bot是纯内存对象**，重启后：
1. 上次的全部消失
2. 按配置数量**重新随机生成一批**
3. **entry 可能完全不同**

所以你 `.pin fix` 清理掉的那个 `Llane (80129)`，
重启后**本来就不会在原地** —— 它是被重新洗牌了。

### 3.2 `.pin` 的意义就是打破这个循环

`.pin` 成功的话，bot 会被写进 `world.creature`，
变成**和普通NPC一样的固定生物**，重启后从表里加载，不再参与洗牌。

**但因为错误1，`.pin` 从来没成功过，所以你从没见过这个效果。**

## 四、修复方案

### 4.1 修 `.pin`：调整顺序（关键）

```
旧（错）：AddNpcBotData -> SaveToDB(被拦) -> ... -> UnsetWanderer
新（对）：UnsetWanderer -> AddNpcBotData -> SaveToDB -> ...
```

**同时加失败回滚**：`UnsetWanderer` 之后如果后续步骤失败，
要把 bot 恢复成游荡状态（`SetWanderer()`），否则它会变成
"不游荡也没落库"的孤儿。

### 4.2 修 `.pin fix`：不再直接 erase

**三种情况分开处理**：

| 情况 | 处理 |
|---|---|
| bot **不在世界里** | 可以安全 erase |
| bot **在世界里**，只有 characters_npcbot | **先让 bot 消失**，再 erase |
| bot **在世界里**，只有 creature | 只删 creature 表，不碰 `_botsData` |

**让 bot 消失的正确姿势**（避免野指针）：

```cpp
bot->CombatStop();
bot->AddObjectToRemoveList();     // 排进删除队列，下个 tick 真正销毁
// 【然后才能】erase
```

**但这里有个时序问题**：`AddObjectToRemoveList` 是**延迟删除**，
同一个 tick 内 bot 对象还活着。所以 erase 必须等到下个 tick。

**更安全的做法**：**只删数据库，不动内存**，然后提示用户重启。

```cpp
// 直接发 SQL，绕过 UpdateNpcBotData
CharacterDatabase.PExecute("DELETE FROM characters_npcbot WHERE entry = {}", entry);
// 内存里的 _botsData 保持不动 -> _botData 指针依然有效 -> 不会崩
// 重启后自然就干净了
```

**代价**：要重启才生效。**但这比崩服强得多。**

### 4.3 `.pin status` 增加说明

明确告诉用户：
- 游荡bot本来就每次重启重新洗牌
- `.pin` 成功后才会固定下来
- 当前是不是真的固定了

## 五、我的三个错误记录

### 错误1：只查了"官方怎么做"，没查"官方的前提条件"

我 step49 照抄 `botcommands.cpp:3860` 的四步，
**但官方那个 `.npcbot spawn` 是对【新建的bot】用的**，
那种 bot 从来就不是 wanderer。

**我把它用在游荡bot上，却没检查 `SaveToDB` 有没有前置条件。**

**规则：照抄一段代码时，必须查清它的【调用前提】，
不能假设换个场景还成立。**

### 错误2：治标不治本

step60 我看到"两个指令判断不一致"就去统一判断，
**没有追问"为什么会产生不一致的状态"**。

**规则：遇到"状态损坏"，先问【谁造成的】，
修完成因再修表象。只做清理工具 = 让用户反复踩。**

### 错误3：删除共享数据前没查谁在引用

`_botsData.erase()` 看着人畜无害，
但 `bot_ai` 在构造时就缓存了指针（`bot_ai.cpp:164`）。

**规则：erase / delete 任何共享容器里的对象之前，
必须 grep 谁持有它的指针/引用。**
