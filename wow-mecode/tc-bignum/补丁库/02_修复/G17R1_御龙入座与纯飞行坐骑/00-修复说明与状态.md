# G17-R1：御龙异步入座与纯飞行坐骑客户端施法门修复

更新时间：2026-08-22

状态：`WINDOWS_BUILD_PASS / CLIENT_DBC_STAGE_PASS / CLIENT_MPQ_NOT_INSTALLED / RUNTIME_NOT_ACCEPTED`

## 1. 已确认的御龙入座根因

`Unit::EnterVehicle()`不是同步完成入座：它先施放硬编码载具光环46598，`Vehicle::AddPassenger()`再把`VehicleJoinEvent`排入玩家事件队列。旧G17-B0在调用`EnterVehicle(dragon, 0)`后立刻检查`GetVehicleBase()`；事件尚未执行时该值必然还不是新龙，于是代码马上销毁龙并回报“进入可控座位失败”。

G17-R1不再做这个同步误判：

- 从实际`VehicleKit::Seats`中寻找`VEHICLE_SEAT_FLAG_CAN_CONTROL`座位，不再假定永远是0号；
- 先调用`EnterVehicle`，再在同一玩家事件队列250ms后验证车辆、座位和`GetCharmerGUID()`控制权；
- 成功后才回报“载具已就绪”；失败时清理并输出精确worldserver日志；
- `GetRider`、`PassengerBoarded`和status均按实际可控座位工作；
- 日志会列出VehicleId、每个seat entry/flags、计划入座、PassengerBoarded和延迟验收结果；
- 将energy cost统一为`uint32`，扣能时显式转成负`int32`，清理旧构建中的C4018。

## 2. 始祖幼龙等纯飞行坐骑为何仍被拒绝

G17-A只修复了服务端`SpellInfo::CheckLocation`。3.3.5客户端自己的`Spell.dbc`仍会读取`AttributesExD`中的`0x04000000`（Only in Outland/Northrend）。混合地面/飞行坐骑可通过包装法术选择飞行子法术，但红色始祖幼龙等纯飞行坐骑会先被客户端本地门阻止，服务端放行逻辑可能根本收不到施法请求。

本批次提供**客户端专用**`Spell.dbc`补丁器：

- 只处理同时具有`0x04000000`且EffectAura包含Mounted(78)、Fly(201)或Mounted Flight Speed(207)的行；
- 只清除该一个bit，不改ID、效果、速度、名称、字符串块或其它记录；
- 服务器DBC必须保持原样，让G17-A继续负责户外/城市/室内/PVP/副本边界；
- 输入输出禁止为同一路径，防止误改服务器DBC；
- 对公开及用户真实的3.3.5a build 12340 zhCN Spell.dbc验证通过：49839行中精确修改110行，包含10个标准始祖幼龙法术59569、59961、59976、59996、60002、60021、60024、61294、63956、63963；输出等长，只有目标AttributesExD字节改变。

用户机器已经生成客户端专用`DBFilesClient\Spell.dbc`：输入SHA-256为`df44e75e...d10f`，输出为`dd250911...64ea`，但准备脚本没有收到ClientRoot，因此目前只在workspace uploads staging中，尚未安装进`D:\WOW`。
