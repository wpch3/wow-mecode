崩溃点（你的本地行号）：

```

```

上游同一行是 `botcommands.cpp:3597`（你本地比上游多 23 行，是之前补丁挤出来的）。

## 一、根因：两个容器，两套生命周期

`move` 命令里有这么一段（上游 3589-3597）：

```cpp
if (!BotDataMgr::SelectNpcBotData(id))      // 查 _botsData
{
    handler->PSendSysMessage("NpcBot %u is not spawned!", id);
    handler->SetSentErrorMessage(true);
    return false;
}

Creature const* bot = BotDataMgr::FindBot(id);   // 查 _existingBots
ASSERT(bot);                                      // <-- 崩在这
```

**上一行用 A 容器做检查，下一行却用 B 容器取值，然后断言 B 一定有。**
这个前提在本仓库根本不成立。

### 两个容器实证

| | `_botsData` | `_existingBots` |
|---|---|---|
| 定义 | `botdatamgr.cpp:54` | `botdatamgr.cpp:58` |
| 查询函数 | `SelectNpcBotData` (`:2927`) | `FindBot` (`:3311`) |
| 装的是什么 | **数据库 `characters_npcbot` 表的行** | **当前内存里活着的 Creature 指针** |
| 谁填 | `LoadNpcBots` `:1055` 读表 / `AddNpcBotData` `:2912` | 只有 `bot_ai.cpp:175` `RegisterBot(me)` |
| 谁清 | `UpdateNpcBotData(NPCBOT_UPDATE_ERASE)` `:3118` | 只有 `bot_ai.cpp:185` `UnregisterBot(me)` |

关键：

```cpp
// bot_ai.cpp:163  构造函数
bot_ai::bot_ai(Creature* creature) : CreatureAI(creature), ...
{
    ...
    if (!IsTempBot())
        BotDataMgr::RegisterBot(me);     // :175
}
// bot_ai.cpp:177  析构函数
bot_ai::~bot_ai()
{
    ...
    if (!IsTempBot())
        BotDataMgr::UnregisterBot(me);   // :185
}
```

`_existingBots` 的成员资格 **完全绑定 bot_ai 对象的生命周期**，
而 `_botsData` 的成员资格 **绑定数据库表的行**。

数据库有行 ≠ 内存里有活着的 Creature。**中间这个缺口就是崩溃。**

### 上游自己也承认这两个会不同步

`botdatamgr.cpp:832`，遍历 `_existingBots` 时还要**额外**判一次 `SelectNpcBotData`：

```cpp
for (Creature const* bot : _existingBots)
{
    if (!bot->IsInWorld() && bot->FindMap() && !bot->IsWandererBot()
        && !!SelectNpcBotData(bot->GetEntry())      // <-- 在 _existingBots 里也可能没数据
        && bot->IsFreeBot())
```

反过来同理。上游在这里防了，在 `move` 里没防 —— 这就是个漏网的上游 bug。

## 二、什么情况下会踩中（你的库正好全占）

`characters_npcbot` 有行，但内存里没有活着的 Creature，至少四条路径：

**1. `creature` 表没有对应实体（你的库刚发生过）**

启动时 `LoadNpcBots` `:1104` 按 entry 查 `creature` 表：

```cpp
infores = WorldDatabase.PQuery("SELECT guid, map, ... FROM creature WHERE id = {}", entry);
if (!infores)
{
    BOT_LOG_ERROR("server.loading", "Cannot spawn npcbot {} (id: {}), not found in `creature` table!", proto->Name, entry);
    continue;                          // <-- 只跳过，_botsData 里那条已经加进去了
}
```

`:1055` 先 emplace 进 `_botsData`，`:1104` 才查 `creature` 表。
**查不到只是 `continue`，数据留在 `_botsData` 里，但永远不会有 Creature、不会有 bot_ai、不会 RegisterBot。**

→ 这跟 **F21 崩服是同一个病根**：`characters_npcbot` 有数据 / `creature` 表没实体。
F21 崩在组队加载，F22 崩在 move 命令，**同一个不一致的两个出口**。

**2. bot 死了 / 尸体被清 / AI 被销毁** —— 析构走 `:185` UnregisterBot，`_botsData` 不动。

**3. bot 所在地图没加载** —— 没有 Map 就没有 Creature 实例。

**4. `.npcbot delete` 之后残留** —— `UpdateNpcBotData(ERASE)` 和 UnregisterBot 时机不同。

## 四、为什么要多加后面两段（不是凑数）

### 第 2 段：游荡 bot 会静默写坏数据

`move` 后面这段（上游 3609-3616）：

```cpp
CreatureData* cdata = const_cast<CreatureData*>(data);
cdata->spawnPoint.Relocate(player);
...
WorldDatabase.PExecute("UPDATE creature SET position_x = ... WHERE guid = {}", lowguid);
```

游荡 bot 是 **spawnId == 0**（`botdatamgr.cpp:210` 用 `LoadBotCreatureFromDB(0, map, true, true, ...)`，
`:460` 注释 `//We do not create CreatureData for generated bots`）。

而 `bot_ai.cpp:246-250` 判定游荡身份就看这个：

```cpp
void bot_ai::InitializeAI() { if (!me->GetSpawnId() && !IsTempBot() && !me->IsSummon()) SetWanderer(); }
```

对游荡 bot 执行 `move`，`lowguid` 是 0 → `UPDATE creature ... WHERE guid = 0`。
`creature` 表 guid 从 1 开始，**不报错、影响 0 行**，你只会看到 "was moved" 却什么都没发生。
更糟的是 500 个游荡 bot 全部 spawnId=0，将来若有 guid=0 的脏行会被反复覆写。

顺带解释 F20 站桩：Creature.cpp:1410/1430 两处 `SaveToDB` 对游荡 bot 直接 `return`，
所以游荡 bot 的坐标本来就**不该**落库，`move` 对它无意义。

### 第 3 段：spawnId=0 时会报错误的提示

原代码 `:3601` `GetCreatureData(lowguid)`，`ObjectMgr.h:1349` 实现是 map 查找，
`spawnId=0` 找不到就返回 nullptr，走到 `LANG_COMMAND_CREATGUIDNOTFOUND`（Language.h:338，"creature guid 0 not found"）。
这个提示会让人以为是 `creature` 表坏了，其实是选错了 bot 类型。提前拦截给准确信息。

## 五、`.npcbot spawn` 是否有同样问题 —— 已查，**不会崩，但有个真 bug**

你说测试 spawn 不会崩，**和源码一致**。`HandleNpcBotSpawnCommand`（上游 3760-3877）全程 **没有调用 `FindBot`**，所以不存在这个断言。它的检查链是：

|---|---|---|
| 3777 | `GetCreatureTemplate(id)` | 正常报错返回 |

### 但 spawn 有一个内存 / 数据泄漏（上游 bug，建议一起修）

`:3860` 先写数据，`:3865` 才可能失败：


`AddNpcBotData`（`botdatamgr.cpp:2908-2920`）是**立刻写库**的：

```cpp

```

一旦 `:3865` 失败，就制造出一条 **`characters_npcbot` 有、内存无 bot_ai** 的记录 ——
**正好就是让 move 崩溃、让 F21 崩服的那种脏数据**。

失败概率不高（要 Create 成功但 Load 失败），但这是**脏数据的源头之一**，你的库已经有这类不一致了。

#### spawn 的可选修复

原文（你本地约 3888-3894，上游 3865-3871）：

```cpp
        if (!creature->LoadBotCreatureFromDB(db_guid, map))
        {
            delete creature;
            handler->SendSysMessage("Cannot load npcbot from DB!");
            handler->SetSentErrorMessage(true);
```

## 七、和 F21 的关系（重要）

F21 和 F22 是**同一个数据不一致的两个出口**：

```
characters_npcbot 有行  +  creature 表无实体
        │
        ├──-> 启动加载组队 ──-> botdatamgr.cpp:1224 ASSERT_NOTNULL ──-> F21 崩服
        └──-> .npcbot move  ──-> botcommands.cpp:3597 ASSERT(bot)  ──-> F22 闪退
```

**F21 的 SQL 清的是数据，F22 的补丁修的是代码。两个都要做。**
只清数据，以后再产生不一致还会崩；只改代码，F21 那条组队记录仍会崩在 `:1224`。

## 八、后续实测：70231 报 "has data but no live creature"（2026-08-06）

补丁装上后不再闪退，改报这条提示。**这是补丁在正常工作**，但暴露了另一个问题。

### 用户实测数据

```
诊断1  -> C类：characters_npcbot 和 creature 表【都有】，不是脏数据
诊断2  -> spawnId=214069, map=0, spawnMask=1, phaseMask=1, ScriptName='wanderer'
诊断3  -> 模板正常
诊断4  -> owner != 0（已被雇佣）
诊断5/6 -> 无异常数据
诊断7  -> 【全部】bot 的 ScriptName 都是 'wanderer'
```

### 根因：A36 对已雇佣的 bot 完全失效

三条源码锁死这个结论：

```cpp
// bot_ai.cpp:20412
void bot_ai::SetWanderer()
{
    if (IAmFree())          // <-- 硬门槛
    {
        _wanderer = true;
        if (botPet)
            botPet->GetBotPetAI()->SetWanderer();
    }
}

// bot_ai.cpp:15379
bool bot_ai::IAmFree() const
{
    if (!_botData->owner)
        return true;        // owner==0 才算 free
    ...
    return false;
}
```

70231 的 `owner != 0` -> `IAmFree()` 返回 false -> **`SetWanderer()` 整个函数空转**。

于是 70231 变成四不像：

| 层面 | 状态 |
|---|---|
| `creature` 表 | `ScriptName='wanderer'`（A36 写的） |
| 内存 `_wanderer` | **false**（被 `IAmFree()` 挡掉） |
| `characters_npcbot.owner` | **!= 0**，是玩家的随从 |

### 为什么 FindBot 找不到它

`bot_ai.cpp:17685`：

```cpp
if (BotCfg::HideBotSpawns() && IAmFree() && !IsWanderer())
```

被雇佣的 bot 跟随主人。**主人下线 -> bot 离开世界 -> `bot_ai` 析构 -> `bot_ai.cpp:185 UnregisterBot(me)` -> 从 `_existingBots` 移除 -> `FindBot` 返回 nullptr。**

**这是正确行为，不是 bug。** `.npcbot move` 的语义是「改固定据点 bot 的 spawn 坐标」，
对已被雇佣的随从没有意义 —— 它的位置由主人决定。

### 结论

1. **F22 补丁本身正确**，把闪退变成了可读提示，无需再改
2. **70231 这条提示是预期内的**，因为它是已雇佣 bot 且主人不在线
3. **真正要处理的是 A36 的适用范围**：`ScriptName='wanderer'` 只对 `owner=0` 的 bot 有效

### A36 的正确用法（三层架构对照）

| 层 | owner | ScriptName | 说明 |
|---|---|---|---|
| 固定据点 NPC | 0 | 空 | 站桩不动 |
| **永久化游荡 bot** | **必须 0** | **wanderer** | A36 的目标 |
| 完全随机游荡 bot | 0 | 不适用（spawnId=0） | 上游原生 |
| 玩家随从 | != 0 | **写了也没用** | 跟随主人 |

跑 `诊断-A36是否失效.sql` 可以看出这批 bot 里有几个是白写的。

如果要让已雇佣的 bot 转为永久游荡 bot，必须先解除雇佣关系（`owner` 置 0），
**但这会影响玩家的随从**，属于业务决策，需要用户确认后再做。

## 九、【更正】第八章的结论是错的（2026-08-06）

第八章说「A36 对已雇佣 bot 失效，`SetWanderer()` 被 `IAmFree()` 挡住」——**这是错的，作废。**

### 错在哪

我只看了 `IAmFree()` 的第一个 return，漏了第二个：

```cpp
// bot_ai.cpp:15379
bool bot_ai::IAmFree() const
{
    if (!_botData->owner)
        return true;                                     // <- 第八章只看了这句
    if (_botData->owner != master->GetGUID().GetRawValue() &&
        !(master->GetGUID().IsPlayer() && _botData->shared_owners.contains(master->GetGUID().GetCounter())))
        return true;                                     // <- 漏了这句，它才是关键
    return false;
}
```

而 bot 构造时 master 指向的是**它自己**：

```cpp
// bot_ai.cpp:163  构造函数
bot_ai::bot_ai(Creature* creature) : CreatureAI(creature), ...
{
    ResetBotAI(BOTAI_RESET_INIT);        // :172
    ...
}

// botcommon.h:610
BOTAI_RESET_MASK_RESET_MASTER = (BOTAI_RESET_INIT | BOTAI_RESET_DISMISS | BOTAI_RESET_UNBIND | BOTAI_RESET_LOGOUT)

// bot_ai.cpp:459-460
if (resetType & BOTAI_RESET_MASK_RESET_MASTER)
    master = reinterpret_cast<Player*>(me);              // master = bot 自己
```

`master` 是 Creature，`master->GetGUID()` 是 Creature GUID，永远 != `_botData->owner`（Player GUID）
-> `:15383` 命中 -> **返回 true** -> `SetWanderer()` 正常执行。

只有主人**真在线**时，`FindMaster()`（`:15330`）才换 master：

```cpp
// bot_ai.cpp:15356
if (Player* player = ObjectAccessor::FindPlayerByLowGUID(guid_low))
{
    ...
    if (SetBotOwner(player))    // :15361  这时 master 才变成真玩家
        return;
}
```

### 正确结论

**A36 是生效的。** 70231 确实是游荡 bot。

### 70231 报 "no live creature" 的真因

游荡 bot 会**跨地图传送**，传送途中不在 `_existingBots` 里：

```cpp
// bot_ai.cpp:18631-18642  游荡bot离家太远就传送
if (IsWanderer())
{
    if (mapid != me->GetMap()->GetId() || _evadeCount >= 50 || ...)
    {
        BOT_LOG_DEBUG("npcbots", "... TELEPORTING to node ... dist {} yd!", ...);
        me->CastSpell(me, WANDERER_HEARTHSTONE);          // :18641
        return;
    }
}

// bot_ai.cpp:7395-7402  施法命中后真正传送
case WANDERER_HEARTHSTONE:
    if (IsWanderer())
    {
        Map* targetMap = (me->GetMap()->GetEntry()->IsContinent() &&
            _travel_node_cur->GetMapId() != me->GetMap()->GetId()) ?
            sMapMgr->CreateBaseMap(_travel_node_cur->GetMapId()) : me->GetMap();
        BotMgr::TeleportBot(me, targetMap, _travel_node_cur, true);   // :7400
        _evadeCount = 0;
    }
    return;
```

`TeleportBot` -> `_teleportBot`（`botmgr.cpp:550`）是**延迟回调**（`:561 AddDelayedTeleportCallback`），
中间 `bot->RemoveFromWorld()`（`:600`）+ `mymap->RemoveFromMap(bot, false)`（`:610`）。

用户之前日志里刷屏的 `TELEPORTING to node ... dist 21114 yd!` 就是这个机制。

**诊断2 里 `creature` 表记的坐标（map=0 暴风城）对游荡 bot 已无意义** ——
它早就跑到别的地图去了。`.npcbot move` 改的是那个已经没用的 spawn 坐标。
