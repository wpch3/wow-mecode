# F21  启动崩溃：`ASSERT_NOTNULL BotDataMgr::FindBot(creature_id)`

```
Loading NPCBot group members...
D:\TrinityCore\src\common\Debugging\Errors.h:80 in ASSERT_NOTNULL_IMPL ASSERTION FAILED:
  pointer
BotDataMgr::FindBot(creature_id)
```

---

## 一、先说结论：**和 F20 无关，是数据库残留**

F20 只改了 `bot_ai.cpp:4310` 一个变量（追击距离），
**和组队数据加载完全没有交集**。

崩溃点在 `botdatamgr.cpp:1224`，是启动时加载 `characters_npcbot_group_member` 表。

---

## 二、根因

### 崩溃那行

`botdatamgr.cpp:1224`：

```cpp
if (Group* group = sGroupMgr->GetGroupByDbStoreId(fields[0].GetUInt32()))
{
    group->LoadCreatureMemberFromDB(creature_id, ...);
    const_cast<Creature*>(ASSERT_NOTNULL(BotDataMgr::FindBot(creature_id)))->SetBotGroup(group, subgroup);
    //                    ^^^^^^^^^^^^^^ 返回 nullptr 就崩
}
```

### `FindBot` 查的是「已在世界里的 bot」

`botdatamgr.cpp:3311`：

```cpp
Creature const* BotDataMgr::FindBot(uint32 entry)
{
    std::shared_lock lock(*GetLock());
    auto it = std::ranges::find_if(_existingBots, [entry](Creature const* bot) { return bot->GetEntry() == entry; });
    return it != _existingBots.cend() ? *it : nullptr;
}
```

`_existingBots` 由 `bot_ai.cpp:175 RegisterBot(me)` 填充 —— **bot 真正 spawn 时才进去**。

### 上游的清理漏了一种情况

`botdatamgr.cpp:1197-1198`：

```cpp
CharacterDatabase.DirectExecute("DELETE FROM characters_npcbot_group_member WHERE guid NOT IN (SELECT guid FROM `groups`)");
CharacterDatabase.DirectExecute("DELETE FROM characters_npcbot_group_member WHERE entry NOT IN (SELECT entry FROM characters_npcbot)");
```

只清理了：
1. 队伍已解散的
2. bot 数据已删除的

**漏了第三种**：

```
entry 在 characters_npcbot 里【有】     -> 躲过清理2
    但 creature 表里【没有】对应记录     -> bot 没能 spawn
    -> _existingBots 里没有它
    -> FindBot 返回 nullptr -> ASSERT 崩服
```

### 你的日志佐证

```
>> Loaded 15 bot data entries      <- characters_npcbot 有 15 条
>> Spawned 15 npcbot(s)            <- 也 spawn 了 15 个
Loading NPCBot group members...    <- 崩在这
```

说明 `characters_npcbot_group_member` 里存着某个 entry，
它在 `characters_npcbot` 里有记录，但**不在那 15 个已 spawn 的 bot 里**。

### 最可能的来源

你之前跑 A35 写入了 `characters_npcbot`，
后来又清理过 `creature` 表（比如 F17 的清理SQL），
导致「有数据无实体」。

---

## 三、修复：跑 `修复.sql`

**最简单的办法（文件里的 2.1，默认就会执行）**：

```sql
DELETE FROM `characters`.`characters_npcbot_group_member`;
```

**清空这张表。**

### 清空的后果

这张表只存「bot 属于哪个队伍」的关系：
- **所有 bot 退出队伍** -> 你重新招募/组队即可
- **不会丢 bot 本身**
- **不会丢装备**（那在 `characters_npcbot` 和 `gear_storage` 里）

### 如果你想保留现有组队关系

用文件里的 **2.2**（先把 2.1 注释掉）：

```sql
DELETE FROM `characters`.`characters_npcbot_group_member`
WHERE `entry` NOT IN (SELECT `id` FROM `world`.`creature`);
```

只删会崩服的那些。

---

## 四、跑完看验证部分

文件最后会输出两个数字，**都必须是 0**：

```
group_member孤儿      = 0
creature无模板记录    = 0
```

都是 0 才能启动服务端。

---

## 五、为什么会积累这种脏数据

这轮我们做了很多 SQL 操作（A35 写入、F17 清理、A36 标记），
**每一步都只管自己那张表**，容易留下跨表不一致。

### 我该做而没做的

**每个改数据的 SQL，末尾都应该带一段「跨表一致性检查」。**

从这次起，A35/A36/F17 那几个文件我会补上统一的检查段。

---

## 六、和三层架构的关系

清空 `group_member` 表**不影响**你的三层架构：

| 层 | 靠什么区分 | 受影响吗 |
|---|---|---|
| 固定据点bot | creature表有 + ScriptName空 | 不受影响 |
| 永久化游荡bot | creature表有 + ScriptName='wanderer' | 不受影响 |
| 完全随机游荡bot | creature表无 | 不受影响 |

**组队关系是另一个维度的数据。**
