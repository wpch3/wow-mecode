## 一、真相：**你的 bot 一直是【正常】的，是我判错了**

你看到的：

```

world.creature   : 无
-> 这个bot的固定数据【已损坏】
```

**这不是损坏。这恰恰是游荡bot应该有的样子。**

### 实证

`botdatamgr.cpp:452`（每生成一个游荡bot就执行）：

```cpp
_botsData.emplace(...);                                  // <- 内存塞一条数据
_botsExtras.emplace(next_bot_id, ...);
...
//We do not create CreatureData for generated bots       // <- :460 官方注释
```

`botdatamgr.cpp:199`（生成前的断言）：

```cpp
ASSERT(bot_data);        // <- 游荡bot【必须】有这条数据，没有就崩服
```

**所以「有内存数据 + 无 creature 记录」= 游荡bot的标准状态。**

我 step60 建模时**没有先去查"正常的游荡bot长什么样"**，
而是**假设**它应该两张表都空 —— 这个假设是错的，
后面 step62 又在错误模型上继续修，越修越糟。

## 二、为什么 `fix` 完再 `pin` 还是叫你 `fix`（死循环）

```
GetPinState()
   -> SelectNpcBotData(entry)
   -> botdatamgr.cpp:2929  _botsData.find(entry)      【读内存】
                                                            |
CleanupBroken()                                             |
   -> DELETE FROM characters_npcbot ...                【只删数据库】
                                                            |
                                                            v
                          内存 _botsData 纹丝不动 -> hasData 永远 true
                                                            |
                                                            v
                                              永远判"损坏" -> 死循环
```

step62 我为了避开野指针崩服，改成"只删库不动内存"——
**这个决定本身是对的**（确实不能 erase），
但它让基于内存的判断永远看不到变化。

> **而且那条 DELETE 是有害的**：游荡bot 的 entry（如 80770）
> 本来就不在 `characters_npcbot` 表里（运行时生成，只在内存），
> 删的是空气。万一撞上真实的已招募bot，还会误删别人数据。

## 三、新的判断模型

**以 `IsWandererBot()` 为权威判据**（`Creature.cpp:3617`），
不再靠"两张表都有没有"。

| 状态 | 内存 `_botsData` | `world.creature` | `IsWandererBot()` | 能做什么 |
|---|---|---|---|---|
| **游荡bot** | 有 | **无** | **是** | `.pin` |
| **已固定** | 有 | 有 | 否 | `.pin off` |
| **已招募** | 有(owner≠0) | 有 | 否 | `.npcbot remove` |
| **真损坏** | **无** | **有** | - | `.pin fix` |

**真正的"损坏"只有一种**：`creature表有 + 内存无`。
这种下次启动 `botdatamgr.cpp:1174` 会 **ABORT_MSG 崩服**，必须修。

**修法是删 creature 表**（那个可以安全删，没人缓存它的指针），
**永远不碰 `_botsData`**。
