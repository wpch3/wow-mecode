# 结案：`54318` = 炉石，`.bf come` 造成的死循环

> 用户 `.bd` 输出：`[GENERIC] 54318`
> 日期：2026-08-02

---

## 一、54318 是什么

**炉石（Hearthstone），10 秒读条。**

源码里 grep 不到这个数字，因为它是 `WANDERER_HEARTHSTONE` 常量。

---

## 二、【真凶】是我的 `.bf come` 造成的，不是 step33

### 游荡 bot 的"回家"机制

```cpp
// bot_ai.cpp:19054  GetHomePosition
if (IsWanderer())
{
    mapid = _travel_node_cur->GetMapId();      // 它的目标路点
    pos->Relocate(homepos);
}
```

**游荡 bot 的"家" = 它当前的目标路点（travel node）**，
不是出生点。

### 触发炉石的条件

```cpp
// bot_ai.cpp:18632
if (mapid != me->GetMap()->GetId() || _evadeCount >= 50 ||
    me->GetExactDist2d(pos) > MAX_WANDER_NODE_DISTANCE ||     // <- 就是这条
    me->GetPositionZ() <= INVALID_HEIGHT || ...)
{
    evadeDelayTimer = 12000;
    me->CastSpell(me, WANDERER_HEARTHSTONE);    // 读条 10 秒
    return;
}
```

**"离目标路点太远"就会念炉石回去。**

### 炉石读完之后

```cpp
// bot_ai.cpp:7395
case WANDERER_HEARTHSTONE:
    if (IsWanderer())
    {
        BotMgr::TeleportBot(me, targetMap, _travel_node_cur, true);   // 传回路点
        _evadeCount = 0;
    }
```

### 死循环形成

```
1. 你 .bf come  ->  我把 bot 传送到【你身边】
2. bot 发现自己离【目标路点】十万八千里
3. 触发 MAX_WANDER_NODE_DISTANCE 判定
4. 开始念炉石（10秒读条）        <- IsCasting() == true
5. 这期间你右键 -> bot_ai.cpp:7704 拦截 -> 对话框关闭
6. 炉石念完 -> 传送回路点 -> 跑了
7. 你再 .bf come 叫回来 -> 回到第 1 步
```

**用户观察到的"他只是在往一个地方跑，不停下来"** —— 完全吻合：
它被传回路点后，继续走它的路线。

**用户观察到的"他也没有吃饭"** —— 对，我上一轮判断错了。
是炉石不是进食。

---

## 三、为什么 `.bd fix` 没用

`.bd fix` 打断了炉石，但：

1. 打断后 bot 仍然远离目标路点
2. 下一个 `GlobalUpdate` 周期，条件依然成立
3. **立刻重新开始念炉石**

**打断只是让它重念一遍，治标不治本。**

---

## 四、正确解法（三选一）

### 解法 A：`.bf come` 时顺便改掉它的目标路点（推荐）

传送 bot 之前，先把它的 travel node 设成离你最近的那个。
这样它到你身边后，就不会觉得"离家太远"。

**需要的 API**：
```
bot_ai.h   GetClosestWanderNode()     bot_ai.cpp:14899 用过
           _travel_node_cur           protected 成员
```

**问题**：`_travel_node_cur` 是 protected，scripts 里改不了。
需要在 bot_ai 加一个 public setter。

### 解法 B：`.bf come` 之后给一段"豁免期"（改动最小）

传送后设置 `evadeDelayTimer`，让它 30 秒内不检查"离家远不远"。

```cpp
// bot_ai.cpp:18617 附近
if (evadeDelayTimer > diff) { evadeDelayTimer -= diff; return; }
```

**只要 evadeDelayTimer 没归零，整个回家检查都不跑。**

`.bf come` 里加一句设置 evadeDelayTimer 即可 ——
但它也是 protected。

### 解法 C：换个思路 —— 不传送 bot，传送你自己（零改动，立刻可用）

```
.bf goto        <- 传送到 bot 那里
```

**bot 待在自己的路点附近，不会念炉石，可以正常对话。**

**这是现在就能用的办法**，不用改任何代码。

---

## 五、立刻可用的测试流程

```
1. .bf              列出游荡bot
2. .bf goto         传送到最近的那个身边（不是把它叫过来）
3. 右键它           应该能正常对话
```

**如果这样能对话，就证明 step33 完全正确**，
问题100%出在 `.bf come` 的传送上。

## 六、教训

### 我这次的连环错误

| 轮次 | 我的判断 | 真相 |
|---|---|---|
| 1 | conf 默认值是 0 | 错 |
| 2 | 传送状态没清除 | 错 |
| 3 | conf.d 没加载 | 错 |
| 4 | 在吃饭喝水 | **错**（是炉石）|

**第 4 次尤其不该错** —— `.bd` 已经显示 `IsCasting=true`，
我却直接假设"吃饭"，没让它打印法术 ID。

**如果第一次做 `.bd` 时就打印法术 ID，第 4 轮就能省掉。**

### 提炼

**诊断工具要一次做到"打印原始数据"，不要做成"打印我的猜测"。**

`.bd` 第一版只报告"IsCasting = true"，这是【结论】。
第二版报告"[GENERIC] 54318"，这才是【原始数据】。

**原始数据不会骗人，结论会带上我的偏见。**

### 更深的一层

**这个 bug 是我自己的工具（.bf come）引入的。**

我做 `.bf come` 是为了方便测试，结果它破坏了游荡 bot 的
内部状态一致性，制造了一个原本不存在的问题，
然后我花了 4 轮去查一个"自己造出来的 bug"。

**教训：测试工具不能改变被测对象的关键状态。**
`.bf goto`（移动观察者）比 `.bf come`（移动被观察者）安全得多。
