## 一、v3 做了什么

| 项目 | v2 | v3 |
|---|---|---|
| 菜单流程 | 选专精 → 应用 | **选专精 → 选职责 → 应用**（两步） |
| 队伍职责 | 无 | **坦克 / 输出 / 治疗** 自己选，系统给推荐，选完记住 |
| 战斗场景 | 无 | **6 档**：自动/任务/刷材料/副本/团本/高级团本 |
| 治疗 | 只能对自己放 | **扫全团，谁血少奶谁，坦克优先，多人受伤切群疗** |
| 自动增益 | 无 | **`.buff` 一键补满 + 连招时自动维持** |
| 驱散解控 | 无 | **自己+队友**，毒/疫病/魔法/诅咒；中控自动解 |
| 打断 | 无 | 目标读条时自动打断 |
| 回蓝 | 无 | 蓝低于 40% 自动用回蓝技 |
| 技能条目 | 517 | **722** |
| 方案总数 | 31 | **558 套**（31专精 × 3职责 × 6场景） |

### 核心思路：专精 × 职责 × 场景

你说的「系统有时候会选错」——所以**职责由你自己定，系统只给推荐**。

同一个专精，选不同职责出来的循环**完全不同**（这是实测输出）：

```
防护战 + 坦克  ->  首技能 = 嘲讽
防护战 + 输出  ->  首技能 = 盾牌猛击
```

场景决定「激进程度」（实测输出）：

| 场景 | AOE门槛 | 保命线 | 救人线 | 省爆发 |
|---|---|---|---|---|
| 做任务/刷怪 | 2 个怪 | 30% | 25% | 否 |
| 聚怪刷材料 | 2 个怪 | 35% | 30% | 否 |
| 5人副本 | 3 个怪 | 45% | 35% | 否 |
| 团本 | 3 个怪 | 55% | 40% | **是** |
| 高级团本 | 4 个怪 | **65%** | **45%** | **是** |

越到高难度：**提前救人、不乱 AOE 拉仇恨、爆发留给 BOSS**。这就是「设置了就能打本」。

## 四、怎么用

### 4.1 配栏（两步菜单）

```
.bar
```

**第 1 步**弹专精：
```
【武器】近战DPS
【狂怒】近战DPS
【防护】坦克  <当前天赋>
【全专精】GM3 全天赋 - 所有技能混合
```

**第 2 步**弹职责：
```
【坦克】嘲讽拉怪 + 减伤自保优先   <推荐>
【输出】纯伤害循环 + 爆发最大化
【治疗】奶队友 + 保自己 + 群疗
返回上一步
```

选完直接配栏。`<推荐>` 是系统按专精给的，`<上次>` 是你上回选的。

分区：
- 第 1 排 = 主循环（坦克是拉怪+输出，治疗是治疗循环）
- 第 2 页 = 爆发
- 右侧栏 1 = 保命/紧急
- 右侧栏 2 = 增益/功能（驱散、打断、回蓝）

快捷用法：
```
.bar auto      跳过菜单，按当前天赋+上次职责直接配
.bar all       全专精
.bar clear     清空
```

### 4.2 连招

```
.combo
```
同样两步菜单。开启后会报当前配置：

```
[连招已开启] 防护 · 坦克 · 高级团本
坦克模式：优先嘲讽拉怪、打断、开减伤，血少自动自保
AOE门槛 4 个怪 / 保命线 65% / 救人线 45%
读条技会等站定再放，移动中自动跳过不断连
```

**执行优先级**（每 500ms 一跳，从上往下找第一个能放的）：

1. **紧急** — 自我解控（真被控住才用）、保命技
2. **治疗** — 治疗职责扫全团；其他职责只自奶
3. **驱散** — 队友身上的毒/疫病/魔法/诅咒
4. **打断** — 目标在读条才用
5. **增益** — 缺什么补什么
6. **回蓝** — 蓝 < 40%
7. **爆发** — 高难度场景只对 BOSS 开
8. **主循环** — 按职责组装的伤害/拉怪循环

```
.combo list    看序列（标了[需站定]/[AOE]/[斩杀]）
.combo off     关闭
```

【立刻补满增益】把该上的 buff 全开一遍

## 六、设计要点

### 6.1 治疗目标怎么选

坦克有 **5% 加权**——同血量下优先奶坦克，但不是无脑偏袒（实测）：

```
坦克60% / DPS 55%  -> 选坦克   （加权后坦克算 55%，并列时坦克优先）
坦克60% / DPS 20%  -> 选DPS    （差距大时救更危险的）
```

怎么认坦克：没有现成的角色标记能读，用**职业 + 血上限**判断
（防护类职业 且 血量 > 自己的 1.2 倍）。认错也不影响正确性，只影响优先级微调。

### 6.2 驱散怎么做的

读 `GetAppliedAuras()`（`Unit.h:1350` public），
逐个看 `AuraApplication::IsPositive()`（`SpellAuras.h:81`），
负面的再查 `SpellInfo::Dispel`（`SpellInfo.h:316`）类型，
和自己驱散技能的 `SPELL_EFFECT_DISPEL` MiscValue 对得上才放。

只处理 4 种标准类型：魔法 / 诅咒 / 疾病 / 中毒。

### 6.3 解控不浪费 CD

自我解控技只在**真的被控住**时才用：

```cpp
uint32 const ccMask = (1u<<MECHANIC_FEAR) | (1u<<MECHANIC_STUN) |
                      (1u<<MECHANIC_ROOT) | ... ;
if (!player->HasAuraWithMechanic(ccMask))
    return 2;   // 没被控，跳过
```

`Unit.h:1425 HasAuraWithMechanic()` 已核实 public。

### 6.4 场景识别

```
Map.h:448 IsRaid() + IsHeroic()/Is25ManRaid()  -> 高级团本
Map.h:446 IsDungeon() + IsHeroic()             -> 高级副本
野外 + Group.h:259 GetMembersCount() > 1        -> 聚怪刷材料
```

全部 public，已核实。

### 6.5 性能

`BuildPlan`结果缓存在按玩家GUID隔离、可显式清理的`PlanCaches()`中，
只有「职业/专精/职责/全专精/场景」变化才重算；关闭、重启、generation变化和logout都会清理。
每500ms的tick不会重复组装数据表，也不会残留不可回收的局部静态缓存。

## 十、v3.1 修复（用户实测反馈）

### 修复 1：`.combo` 无限释放增益（圣骑士强效力量祝福）

**你报的现象**：圣骑士一直重复放强效力量祝福。

**根因**：`CastSpell` 返回 `SpellCastResult`（`Object.h:532`），但我**没有检查返回值**。

强效力量祝福需要消耗材料【王者之符】，没有材料时服务端返回
`SPELL_FAILED_REAGENTS` —— 但代码把它当成功了。而技能没真的放出去，
`HasAura` 永远为假，于是每 500ms 重试一次，无限刷屏。

**修复**：检查返回值 + 失败退避表。

```cpp
SpellCastResult res = player->CastSpell(castTarget, real, CastSpellExtraArgs(false));
if (res != SPELL_CAST_OK)
{
    CombatHelper::MarkFailed(player, real, res);   // 记一笔，短期不再试
    return false;                                   // 继续往下找别的技能
}
CombatHelper::ClearFailed(player, real);
```

退避时长按失败原因分档：

| 失败原因 | 退避 | 理由 |
|---|---|---|
| 缺材料 / 缺物品 / 形态不对 | **5 分钟** | 这次战斗基本没戏 |
| 距离远 / 视线挡 / 不在正面 / 正在读条 | **2 秒** | 走近点就能放 |
| 没蓝没怒气 | **5 秒** | 等资源回来 |
| 其他 | 10 秒 | |
| 连续失败 3 次 | 拉长到 **60 秒** | 兜底防高频重试 |

成功一次就立刻清除退避；重开 `.combo` 或下线也会清空，
给之前放不出的技能一次新机会。

**实测对比**（`bugfixtest`）：

| | 20 跳内尝试次数 |
|---|---|
| 修复前 | **20 次**（每跳都试，刷屏） |
| 修复后 | **1 次** |

且验证了「能成功的技能 10 跳照放 10 次」——退避不会误伤正常技能。

### 修复 2：打断优先蓄力大招（你要求的新功能）

不是见到读条就打断，而是**扫描周围所有正在读条的敌人，挑最危险的打**。

打分规则：

```
基础分 = 总读条时间（毫秒）    读条越长 = 越是大招
群体技              × 2        AOE 更致命
正在打我的          + 2000
剩余读条 > 1 秒     + 1000     打得中
```

跳过两种不值得打的：
- **剩余读条 < 0.3 秒** —— 打断来不及，浪费 CD
- **`PreventionType != SILENCE`** —— 本来就打不断的法术

打断成功会在聊天框提示：
```
[打断] 火焰使者 的 烈焰风暴  (群体技)
```

**实测**（`bugfixtest`）：

| 场景 | 结果 |
|---|---|
| 小火球(1秒) vs 毁灭陨石(5秒) | 打断**毁灭陨石** |
| 再加烈焰风暴(3秒群体) | 打断**烈焰风暴**（群体加权后分最高） |
| 同为3秒，一个打我一个打别人 | 打断**冲我来的** |
| 只剩 0.1 秒 | **不打**，不浪费 |
| 无法打断的法术 | **不打**，不浪费 |

## 十一、v3.2 —— `.buff` 与 `.combo` 冲突（用户精准定位）

> 你的原话：「不是 .combo 的主要问题，是 buff 功能自动补增益，
> 这两者出现了冲突，关闭 buff 自动补增益连招就正常了」

**你判断对了。** v3.1 我只修了 `.combo` 内部的施法路径，
`.buff` 是另一条独立路径，完全没走到那个修复。核实后发现共 **4 个根源**：

### 根源 1：`.buff` 队列绕过了退避表

`.buff now` 用 `EventProcessor` 排队施法，那些 lambda 是**独立事件**，
既不检查 `CastSpell` 返回值，也不查 v3.1 加的退避表。

所以缺材料的祝福在这条路上照样无限撞墙。

| | 连按 10 次 `.buff` 的实际尝试 |
|---|---|
| 修复前 | **10 次** |
| 修复后 | **1 次** |

### 根源 2：`lastBuffTry` 声明了却从未使用

v3 我加了这个限流字段，但**忘了在 `ComboTick` 里用它** ——
结果 combo 每 500ms 都在尝试补 buff。

| | 10 秒内补 buff 尝试次数 |
|---|---|
| 修复前 | **20 次**（每 0.5 秒） |
| 修复后 | **4 次**（3 秒限流） |

### 根源 3：两套系统抢 GCD（你说的"冲突"本体）

`.buff` 队列每 **1.6 秒**放一个，`.combo` 每 **0.5 秒**也在放 ——
两边互相打断，谁都放不干净，表现就是祝福反复重放。
**关掉 `.buff` 反而正常，正是因为少了一个抢施法的。**

修复：`.buff now` 会记一个 `buffQueueUntil` 时间窗，
期间 `ComboTick` **完全让路**，补完自动接管。

实测：队列运行 4.8 秒期间，combo 抢施法从多次降到 **≤1 次**。

### 根源 4：`HasAura` 只认精确 rank

`Unit::HasAura()`（`Unit.cpp:4793`）只匹配**精确 spellId**。

祝福是 rank 链（19740 初级 → 25782 强效）。身上挂着低阶版本、
或队友给的版本时，`HasAura(25782)` 返回 false → 误判"没有" → 重复放。

修复：新增 `HasAnyRankAura()`，沿 `GetFirstSpellInChain` / `GetNextSpellInChain`
（`SpellMgr.h:594/596`，已核实 public）**逐阶检查**，任意一阶存在就算有。

## 十二、v3.3 —— 用户实测的 4 个问题

### 问题 1：脱战时每 3 秒补一次 buff，多余消耗

**两层原因，都修了：**

1. **限流太短** —— v3.2 设的 3 秒。buff 是分钟级增益，3 秒一查太频繁。
   → 放宽到 **15 秒**。

2. **只看"有没有"，不看"还剩多久"**（治本）——
   某些 buff 会出现瞬时空窗，`HasAura` 一假就重上。
   → 新增 `AuraRemainMs()`，沿 rank 链查剩余时长：

   | 返回值 | 含义 | 行为 |
   |---|---|---|
   | `-1` | 永久光环（圣印/光环/姿态） | **绝不重上** |
   | `> 5 分钟` | 还很久 | 不重上 |
   | `0` | 真没有 | 才去上 |

   用到 `SpellAuras.h:156 GetDuration()` / `:161 IsPermanent()`（已核实 public）。

**实测**：60 秒内补 buff 尝试 **20 次 → 4 次**。

### 问题 2：治疗技能完全没被使用（最严重）

查出来是 **3 个根因叠加**：

**根因 A — plan 缓存是全局单份（多人服真 bug）**

```cpp
static thread_local CombatSpec::BuiltPlan plan;   // 所有玩家共用一份！
```

A 是治疗、B 是输出，两人同时开连招时**互相覆盖缓存** ——
治疗拿到了输出方案，治疗技根本不在里面。
→ 改成 `unordered_map<GUID, PlanCache>`，**按玩家分开存**。

**根因 B — 触发条件有逻辑漏洞**

旧代码外层判断 `(role==HEALER || 自己血少)`，内层又套
`allow = (role==HEALER || 目标是自己)`。而 `PickHealTarget`
挑出来的通常是**队友**，于是层层过滤后经常一次都进不去。

→ 拆成两条清晰路径：

```
治疗职责  -> 无条件扫全团，谁血少奶谁
其他职责  -> 只在自己血少时自奶
```

**根因 C — 治疗施法没检查返回值**

治疗那段直接 `CastSpell` 不看结果，失败了也不换下一个技能。
→ 接入退避表，失败自动换下一个治疗技。

**实测**：治疗职责下治疗技排第 1，共 9 个；自己满血也会扫全团奶人。

## 十三、v3.4 —— 猎人只剩普攻、法师只剩火焰冲击

> 你的原话：「猎人发现只有普通攻击，奥术射击都没有」
> 「法师也是除了火焰冲击没看到用其他的技能」

**先说结论：数据表没问题**（奥术射击、火球术一直都在表里）。
问题出在 **v3.1 我引入的退避表反噬了自己**。

### 根因：退避表的计数只增不减

```cpp
++fi.count;
if (fi.count >= 3 && cd < 60000)
    fi.untilMs = now + 60000;      // 拉黑 60 秒
```

`count` **永远不会清零**。任何技能因为**临时原因**失败 3 次，
就被拉黑 60 秒；战斗时间越长，被拉黑的技能越多，
最后只剩下那些不会失败的技能 —— 这就是"只有普通攻击"。

**猎人为什么最惨**：射击技有**最小射程**（死亡区）。怪一贴脸，
8 个射击技全部返回 `SPELL_FAILED_TOO_CLOSE`。而我压根没处理这个错误码，
它落到 `default` 分支 = 10 秒退避，三轮就全部拉黑。

**法师同理**：移动中读条技被判 `SPELL_FAILED_MOVING`，累计后全灭，
只剩瞬发的火焰冲击。

### 修复 1：区分「瞬态失败」和「硬失败」

| 类型 | 错误码 | 退避 | 累计计数 |
|---|---|---|---|
| **瞬态** | 太近 / 太远 / 视线 / 朝向 / 移动中 | **0.8 秒** | **不累计** |
| **瞬态** | 正在读条 / 还没好 | **0.5 秒** | **不累计** |
| **瞬态** | 没蓝没怒 | 2 秒 | 不累计 |
| **瞬态** | 目标状态不对 | 3 秒 | 不累计 |
| 姿态 | 形态不对 / 需要站立 | 15 秒 | 累计 |
| **硬失败** | 缺材料 / 缺弹药 / 武器不对 | **5 分钟** | 累计 |

新增处理的错误码：`TOO_CLOSE`、`NO_AMMO`、`NEED_AMMO`、
`EQUIPPED_ITEM_CLASS`（猎人没弓、战士没盾这类）。

### 修复 2：计数会超时清零

```cpp
if (fi.lastFailMs && now - fi.lastFailMs > 30000)
    fi.count = 0;      // 30 秒没失败过 -> 说明它是能用的，重新开始
```

再也不会出现「打了十分钟，技能越用越少」。

### 修复 3：射程预检（治本）

放技能之前**先量距离**，够不着/太近直接跳过 —— 连失败都不产生，
自然也就不会进退避表。

```cpp
float dist   = player->GetExactDist2d(target);
float maxRng = si->GetMaxRange(false);
float minRng = si->GetMinRange(false);   // 猎人死亡区

if (maxRng > 0.0f && dist > maxRng) return 2;   // 太远
if (minRng > 0.0f && dist < minRng) return 2;   // 太近
```

`SpellInfo.h:483 GetMinRange` / `:484 GetMaxRange`（已核实 public）。
