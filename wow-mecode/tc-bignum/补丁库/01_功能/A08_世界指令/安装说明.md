## 二、保护系统（按你的设计做的）

### 主城判定不用手写列表

查到 `AREA_FLAG_CAPITAL = 0x100`（`DBCEnums.h:255`），
暴雪已经给**所有主城**打好标记了：

> 奥格瑞玛 / 暴风城 / 雷霆崖 / 幽暗城 / 达纳苏斯 / 埃索达 / 银月城

**一个 flag 全覆盖**，而且以后你加新种族主城，只要 DBC 里打了这个 flag
也会自动生效，不用改代码。

### 三档独立开关

| 档 | 覆盖范围 | 默认 | 指令 |
|---|---|---|---|
| 主城 | 全种族 7 个主城 | **开** | `.protect city off` |
| 圣所 | 达拉然 / 沙塔斯等 | **开** | `.protect sanctuary off` |
| 小镇 | 所有带旅店的镇 | 关 | `.protect town on` |
| 友方 | 不打友方单位 | **开** | `.protect friendly off` |
| 只删GM的 | 保护原版 NPC | **开** | `.protect gmonly off` |

```
.protect            查看当前所有状态
.protect all off    一次关掉所有区域保护
```

> **玩家永远受保护，不提供关闭选项。**

### 半径规则（按你的要求）

- **无上限** —— 填 50000、999999 都接受
- **最低 1 码** —— 比 1 小会收敛到 1（避免填 0 无意义）
- **覆盖所有地图** —— 不限制野外/副本

### 二次确认会列出未开启的保护

```
.killr 500

===== 危险操作确认 =====
秒杀周围所有敌对生物
  范围：500 码   影响：247 个目标
  当前位置：龙骨荒野

保护状态：
    主城保护   [开] 全种族7个主城
    圣所保护   [开] 达拉然/沙塔斯等
    小镇保护   [关] 带旅店的小镇  <-- 未开启
    友方保护   [开] 不打友方单位
    玩家保护   [开] 永不伤害玩家

确认执行请重复一次并加 confirm
（10 秒内有效；用 .protect 改保护设置）
```

再输 `.killr 500 confirm` 才真执行。

**确认不可跨参数复用** —— 你先确认了 `.killr 100`，
再输 `.killr 9999 confirm` 不会直接执行，得重新确认。这是防误操作的。

在保护区里执行会**直接拒绝**并告诉你关哪个开关：

```

要在这里执行，先关掉对应保护：
.protect city off
```

## 三、永不误伤清单

无论什么设置，这几类**绝对不会**被杀或删：

| 类型 | 判定 API |
|---|---|
| **NPCBot 和它的宠物** | `Creature.h:394 IsNPCBotOrPet()` |
| 玩家宠物 | `IsPet()` |
| 图腾 | `IsTotem()` |
| 触发器（隐形的） | `IsTrigger()` |
| 玩家 | 只搜 Creature，压根不碰 Player |

> NPCBot 这条是重点 —— 你服务器大量用 bot，
> 误删会直接坏档，所以在收集阶段就排除了。

### `.npcclean` 的 gmOnly 口径

| 模式 | 行为 |
|---|---|
| `gmonly = 开`（默认） | **只清临时召唤**（`.npc add temp`、技能召唤的） |
| `gmonly = 关` | 连数据库刷点一起删（含原版 NPC，**需重启才能恢复**） |

关掉时确认提示会额外警告一行。

## 九、v2 修复（用户实测）

### 修复 1：`.raidbuff` 没给 bot 上 buff

**根因**：Group 里**玩家和 bot 是两条独立链表**。

```cpp
GetFirstMember()    -> GroupReference    -> Player*     // Group.h:257
GetFirstBotMember() -> GroupBotReference -> Creature*   // Group.h:202
```

旧代码只遍历了前者。NPCBot 是 Creature，**压根不在那条链表里**。

**实测**：2 玩家 + 3 bot 的队伍，旧逻辑只收集到 **2 个**。

**修法**：
- 两条链表都遍历，输出改成 `Unit*`（玩家和 bot 一起装）
- **顺带补了没组队的情况** —— 玩家带 bot 但没开队伍时，
  扫周围 60 码内自己的 bot（靠 `IsNPCBotOrPet()` 识别）
- 完成提示会额外报"其中 N 个是 NPCBot"

现在结果：**5 个全覆盖**。

### 修复 2：`.service` 阵营和职业都不对

**根因**：旧做法**写死 entry**（8719/8721/3494/2119），两个问题：
1. 这些是**特定阵营**的 NPC，联盟号召出部落银行家没法交互
2. entry 对应的模板职业/外观不一定匹配那个服务

**修法**：不再依赖 entry 本身，改成**召唤后直接赋予服务标志**。

```cpp
c->SetFaction(FACTION_FRIENDLY);           // 35，两阵营都能用
c->ReplaceAllNpcFlags(NPCFlags(s.flags));  // 服务能力靠 flags
c->SetName(s.cn);                          // 名字直接改中文
```

服务能力由 `UNIT_NPC_FLAGS` 决定，**和 entry 是什么无关**：

| 服务 | flags |
|---|---|
| 拍卖师 | `GOSSIP \| AUCTIONEER` |
| 银行家 | `GOSSIP \| BANKER` |
| 修理商人 | `GOSSIP \| REPAIR \| VENDOR` |
| 邮箱 | `GOSSIP \| MAILBOX` |

用 `ReplaceAllNpcFlags`（不是 `SetNpcFlag`）—— 它会**清掉模板自带的旧标志**，
避免银行家身上还挂着拍卖行功能。

召唤出来的名字直接是「拍卖师」「银行家」「修理商人」「邮箱」。

## 十、v3 修复：服务 NPC 改用独立 entry

> 用户实测 v2：「出现了四个拍卖师费奇，一个有拍卖功能，其他的甚至对话都没有」

### v2 为什么失败

我在 v2 用了「召唤同一个 entry（8719），再改 flags 和名字」的做法。
**这条路根本走不通**：

- `SetName()` 只改**服务端内存**
- 客户端显示的名字来自它自己的 **CreatureCache，按 entry 查**
- 客户端同样缓存了该 entry 的 npcflag

所以四个召唤物在客户端眼里都是 entry 8719 =「拍卖师费奇」，
而且只认 8719 原本的拍卖功能，另外三个连对话都弹不出来。

**教训**：凡是客户端要显示/交互的属性（名字、npcflag、模型），
都必须落到 entry 上，服务端改内存骗不过客户端缓存。

## 十一、v3.1 修正：SQL 报 1064

> 用户报错：`error near 'rank, dmgschool, BaseAttackTime...' at line 4`

### 两个问题

**1. `rank` 是 MySQL 8.0 保留字**

MySQL 8.0 引入窗口函数后，`RANK()` 成了保留字，
当列名用必须加反引号：

```sql
speed_walk, speed_run, scale, `rank`, dmgschool, ...
```

**2. 我上一版的列名是照 C++ 结构体写的，和真实表对不上**

对着 `CreatureData.h` 的 `CreatureTemplate` 结构体写，
但**结构体字段 != 数据库列名**。上一版多了
`trainer_type/trainer_spell/trainer_class/trainer_race`、
`resistance1-6`、`spell1-8`（这些在 3.3.5 的表里不存在），
少了 `spell_school_immune_mask`、`StringId`。

### 修法

直接对着 `sql/base/dev/world_database.sql:622` 的真实建表语句逐列核对。

**校验结果**：

| 检查项 | 结果 |
|---|---|
| 真实表列数 | 59 |
| 本 SQL 列数 | **59** |
| 漏掉的列 | **无** |
| 多余/错误的列 | **无** |
| 列顺序与表一致 | **是** |
| 6 行数据每行值数 | **59 / 59 全匹配** |
| MySQL 解析器验证 | **通过** |
| `rank` 识别为列名 | **是**（不是函数） |

用 sqlglot 的 MySQL 方言解析器做的完整语法验证，不是肉眼看。

### 顺带确认你 SQL 客户端的三个脾气

| 脾气 | 本文件 |
|---|---|
| 只执行光标所在语句 | 全文**只有 1 条语句** |
| 吞掉反引号里的点号 | 用 `world.creature_template`，**库名不带反引号** |
| 不执行 USE | **没有 USE 语句** |
| 注释里不能有分号 | 已确认无分号 |

直接把光标放在 `REPLACE INTO` 上执行即可。

### 顺带对齐可见性字段

拿 **entry 70000 Lagretta**（NPCBot 招募员，可见可对话的中立 NPC）
做参照，把差异字段对齐：

### 教训

## 十三、v3.3：商人没商店 / 修理没修理 / 邮箱不是邮箱

> 用户实测：旅店、银行、拍卖行**能用**，另外三个不行。

这个对比很关键 —— 能用的那三个和不能用的三个，走的是**两套完全不同的机制**。

### 为什么银行/拍卖/旅店本来就能用

这三个是**客户端硬编码**按 npcflag 直接弹窗的，不需要任何额外配置。

### 三个失败原因（都在源码里查到依据）

**根因 1：修理和商店按钮由 Gossip 菜单驱动**

```cpp
// Player.cpp:14163  遍历 gossip_menu_option，按 OptionNpcFlag 匹配
if (!(itr->second.OptionNpcFlag & npcflags)) continue;

// Player.cpp:14170  GOSSIP_OPTION_ARMORER = 15   修理
// Player.cpp:14177  GOSSIP_OPTION_VENDOR  = 3    商店
```

**光有 npcflag 不够**，还得在 `gossip_menu_option` 表里有对应记录，
菜单里才会出现那个按钮。

**根因 2：商人必须有货**

```cpp
// Player.cpp:14179
VendorItemData const* vendorItems = creature->GetVendorItems();
if (!vendorItems || vendorItems->Empty())
{
    TC_LOG_ERROR("sql.sql", "... has UNIT_NPC_FLAG_VENDOR set, but has an empty trading item list.");
    canTalk = false;      // 直接隐藏商店选项
}
```

空货架不但不显示，还会往日志刷错误。

**根因 3：邮箱根本不能用 NPC 做**

`UNIT_NPC_FLAG_MAILBOX` 在 3.3.5 服务端**全库 grep 没有任何处理代码**。

邮箱是 **GameObject**（`GAMEOBJECT_TYPE_MAILBOX = 19`，`SharedDefines.h:1674`），
不是 Creature。给 NPC 挂这个 flag 完全无效。

### 修法

| 服务 | 改动 |
|---|---|
| 修理匠 960003 | 挂 `gossip_menu_id = 96003` + 加 ARMORER/VENDOR 选项 + 6 件货 |
| 商人 960007 | 挂 `gossip_menu_id = 96007` + 加 VENDOR 选项 + 10 件货 |
| 邮箱 | 改用 **GameObject 184137**（官方邮箱），走 `SummonGameObject` |

代码侧给 `Svc` 加了 `isGO` 标志，邮箱走 GO 分支：

```cpp

player->SummonGameObject(184137, x, y, z, o, rot, Seconds(300));
```

这个写法和官方 `SpellEffects.cpp:3622` 完全一致。

## 十四、v3.4 修正：MenuID 溢出（1264）

> 用户报错：`Data truncation: Out of range value for column 'MenuID' at row 1`

### 根因：同一个概念，两张表类型不一样

```sql
creature_template.gossip_menu_id   int unsigned        上限 4294967295
gossip_menu.MenuID                 smallint unsigned   上限 65535   <-- 这个
gossip_menu_option.MenuID          smallint unsigned   上限 65535
```

我按 entry 段（960001）的思路顺手编了 96001 当 MenuID，
**超出 smallint 上限**直接被 MySQL 拒绝。

**教训**：不能因为「entry 能用 960001」就假设「MenuID 也能用 96001」——
必须按目标列的实际类型来。

### 修法

MenuID 段改用 **63001 / 63003 / 63007**（都在 65535 以内）。

`creature_template.gossip_menu_id` 里的引用也同步改了，
两边必须一致否则菜单挂不上。

> entry 保持 960001-960007 不变 —— `creature_template.entry`
> 是 `int unsigned`，960001 完全合法。

### 顺便做了个工具防止再犯

`tools/check_sql_range.py` —— **自动校验 SQL 里每个数值是否超出列类型范围**。

它会拉真实建表语句，逐表逐列比对：

```bash
python3 tools/check_sql_range.py sql/38_service_npc_gossip.sql
```

反向验证过有效（用旧的 96001 测试，能准确报出 6 处溢出）：

```
[FAIL] bad_test.sql
        gossip_menu.MenuID 第1行 值 96001 超出 smallint unsigned 范围 [0, 65535]
        ...
```

以后交付 SQL 前跑一遍，这类 1264 就不会再出现。
