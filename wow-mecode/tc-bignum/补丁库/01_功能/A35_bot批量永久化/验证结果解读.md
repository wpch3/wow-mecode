## 一、验证1 的 "0 vs 5" —— **大概率不是问题，是我SQL口径写歪了**

### 我那条 SQL 两边口径不一样

```sql
-- 左边：只数 owner = 0（无主的）
(SELECT COUNT(*) FROM characters_npcbot WHERE owner = 0)

-- 右边：不看 owner（含被玩家招募的）
(SELECT COUNT(*) FROM creature c JOIN creature_template_npcbot_extras e ...)
```

**左边卡了 `owner=0`，右边没卡。** 两个口径当然对不上。

### 你那 5 条最可能是【你自己招募的 bot】

招募的 bot（`owner > 0`）：
- 在 `characters_npcbot` 里 -> 但 `owner != 0`，**不计入左边**
- 如果它们也有 `creature` 表 spawn 记录 -> **计入右边**

-> **0 vs 5 完全说得通，不是数据坏了。**

### 真正该看的是验证2

```
验证2  creature有但npcbot表没有 = 0
```

**这个才是崩服判据**（对应 `botdatamgr.cpp:1170` 的 ABORT_MSG）。
**你是 0，说明没问题。**

### 跑 `02_诊断验证1和3.sql` 确认

那个文件的 **D 段**会用**同一口径**重新对比，
并且 **A 段**会把那 5 条逐条列出来，告诉你每条的身份：

```
【危险】npcbot表没有它    <- 真问题
正常：被玩家招募的bot      <- 你大概率是这个
正常：无主的固定bot
```

### 先说不会崩服的证据

`ObjectMgr.cpp:2202-2206`（`LoadCreatures` 里）：

```cpp
CreatureTemplate const* cInfo = GetCreatureTemplate(entry);
if (!cInfo)
{
    TC_LOG_ERROR("sql.sql", "Table `creature` has creature (GUID: {}) with non existing creature entry {}, skipped.", guid, entry);
    continue;                    // <-- 【只是跳过，不崩】

```

**执行顺序（实查 World.cpp）**：


**所以那条记录只会在启动日志里刷一条 error，不会 ABORT_MSG。**

> 我之前在 F17 说"会崩服"是**说重了**。
