# 修复：`.pbot spawn` 上线闪退

## 先回答你的疑问：为什么文件改了 VS 里还有

**不是两份文件，是同一份文件的两个视图。**

```text
磁盘上的 bot_ai.cpp        <- 你用外部编辑器改的
VS 内存里的 bot_ai.cpp     <- VS 打开标签页时缓存的副本
```

VS 打开文件后会在内存保留一份。**你在外部改磁盘文件，VS 不会自动刷新
已打开的标签页**（有时会弹"文件已在编辑器外修改，是否重新加载"，
但如果你之前点过"不再提示"，或者标签页不在前台，就不会弹）。

**最要命的是**：这时你在 VS 里按 Ctrl+S，
它会把**内存里的旧内容写回磁盘**，把你外部的修改覆盖掉。

所以你"去 VS 里删除才成功" —— 因为 VS 那份才是最后写进磁盘的。

### 以后怎么避免

```text
方案A（推荐）：全程在 VS 里改，不用外部编辑器
方案B：外部改之前，先在 VS 里关掉那个文件的标签页
方案C：外部改完后，VS 里对着标签页右键 -> 关闭 -> 重新打开
```

**这也解释了之前那次 C2011** —— 编译器读到的是被 VS 覆盖回去的旧版本。

## 闪退根因：`TryBotRequest` 在 bot 刚上线时就跑

### 缺陷1：计时器初值是 0，一上线就执行

```cpp
uint32& timer = _pbotRequestTimer[bguid];
if (timer > diff)
```

`std::unordered_map::operator[]` 对不存在的 key 会**默认构造**，
`uint32` 默认是 **0**。

所以新 bot 第一次进这个函数时 `timer = 0`，
`0 > 1000` 为假 -> **直接往下跑**。

而 `.pbot spawn` 是异步登录，bot 刚进世界那一两秒里：

```text
GetGroup()          可能返回野指针（组数据还没同步完）
GetSession()        可能为空
GetMapId()          地图还没设好
装备数据            还在从 DB 加载
```

### 缺陷2：遍历装备时没判 bot 是否真的就绪

`PBotDecideRequest` 里：

```cpp
Item* eq = bot->GetItemByPos(INVENTORY_SLOT_BAG_0, i);
```

bot 登录过程中装备容器可能还没填充，
`GetItemByPos` 在某些中间态会访问未初始化的数组。

## 修法：两处改动

### 改动1：给新 bot 一个初始延迟

文件：`pbot_autoaccept.cpp`

搜索原文：

```cpp
static void TryBotRequest(Player* bot, uint32 diff)
{
    ObjectGuid bguid = bot->GetGUID();

    uint32& timer = _pbotRequestTimer[bguid];
    if (timer > diff)
    {
        timer -= diff;
        return;
    }
    timer = 0;

    if (!bot->IsInWorld() || !bot->IsAlive() || bot->IsInCombat())
        return;
```

替换为：

```cpp
static void TryBotRequest(Player* bot, uint32 diff)
{
    if (!bot || !bot->IsInWorld() || !bot->GetSession())
        return;

    ObjectGuid bguid = bot->GetGUID();

    // 新 bot 首次进来：给 60-120 秒缓冲，等它完全登录好再考虑索要。
    // 不这么做的话，map::operator[] 默认构造出 0，会立刻往下跑，
    // 此时组队/地图/装备数据都可能还没就绪 -> 崩溃。
    auto titr = _pbotRequestTimer.find(bguid);
    if (titr == _pbotRequestTimer.end())
    {
        _pbotRequestTimer[bguid] = urand(60000, 120000);
        return;
    }

    uint32& timer = titr->second;
    if (timer > diff)
    {
        timer -= diff;
        return;
    }
    timer = 0;

    if (!bot->IsAlive() || bot->IsInCombat())
        return;
```

**关键**：用 `find()` 而不是 `operator[]`，
第一次见到这个 bot 时**先记下延迟就返回**，不往下走。

## 抓崩溃日志（最准的办法）

闪退时会在这里生成崩溃转储：

```text
D:\TC-Build\bin\RelWithDebInfo\Crashes\
```

找**最新**的 `.txt` 文件，打开后找这一段：

```text
Call stack:
Address  Frame    Function            SourceFile
...
```

**把 Call stack 前 15 行贴给我**，能直接定位到是哪个函数崩的。

如果没有 Crashes 文件夹，看 `Server.log` 最后 30 行。

## 我的责任

第6步我写 `TryBotRequest` 时用了 `_pbotRequestTimer[bguid]`，
**没想到 map 的 operator[] 会默认构造出 0**，
导致新 bot 一上线就执行完整逻辑。

A20 的 `_careTimer` 是 bot_ai 的**成员变量**，在构造函数里
`urand(20000, 40000)` 初始化过，所以没这个问题。
我照搬逻辑时漏掉了"全局 map 没有构造函数"这个差异。

**规则**：用 `map[key]` 做计时器时，必须先 `find()` 判断是不是首次，
不能依赖默认值。
